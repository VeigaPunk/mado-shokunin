# CriticNoHarmDiff — corpus-diff no-harm proof has three real defects: biased drift exclusion, relabels counted as additions, and no relabel/join key

Scope: the guard "a whole-corpus diff of the `9c54c56` and final tools loses 0 findings and classes every added row" (SCORECARD.md, "Round 20 — declared claims", C1 admission guards) and its harness `.ufo/waves/round-20/corpus-diff.py` (already written; read at worktree bytes). Compared tool blobs extracted read-only: base `9c54c56a6a7528675027b7f628f97a1b8d1b8e8d` → `/tmp/cnd/tw-base.py` sha256 `c1ae45a7573e536bdb8ad410f36782aaad9832ecae6a95b2f5c7f823d13c70cd` (1,314 lines, CLASSES = host_mutation/package_query/live_probe, `/tmp/cnd/tw-base.py:61`); harmed `1f7f995…` → `/tmp/cnd/tw-r19.py` sha256 `367be94773d8fec5e6df91f80ac777070c407c1128f7c75b3dcaa26cc83fdb4d` (2,128 lines, adds tool_install/vcs_write, `:113`). Both emit per-file `sha256` in `files[]` (`tw-base.py:758`, `tw-r19.py:1536`) — the harness ignores this field; that is the cheapest unused fix on the table.

## D1 — The drift window is per-file-scan sized, so "stable" is biased toward excluding exactly the transcripts that matter (counterexample, live)

`corpus-diff.py:173-184` runs **two subprocesses per corpus file** (`python3 -I tool --scan FILE`, sequential). The corpus is now 5,714 `.jsonl` files under `/home/vgpnk/.omp/agent/sessions/-Projects-shokunin` (`find … -name '*.jsonl' | wc -l`; was 4,821 in round 19). Round 19 measured ~37–55 s for a *whole-corpus single-process* scan (`w2/reports/RerunPrecision.md:56-59`). Per-file subprocess overhead (interpreter start + tool parse ≈ 0.15 s minimum, ×2) alone is ≈ 29+ minutes; realistically an hour-plus. The before/after digests at `:159` and `:186` bracket that entire window, so the stable set shrinks by every file touched in it — and the files touched in it are the live ones.

Counterexample (verified): the live round-20 session root `…/2026-10-20T12-57-31-587Z_01a15963-70c3-7390-a1b4-7911b9506d07/MadoR20/` holds 143 seat transcripts that are being appended *now*. `CasePureBuiltins-3.jsonl` alone contains 73 `pacman` occurrences including literal `subprocess.run(['pacman'…` inside eval-code (grep of the file; it builds census fixtures). These are precisely the files carrying (a) self-referential fixture text and (b) authorized `git commit`-in-/tmp writes — the rows this guard exists to classify — and D1's biased exclusion drops them first. "Loses 0 findings on the stable set" then silently means "loses 0 where we didn't look."

Smallest safe correction: snapshot-pin the corpus — byte-copy (not hardlink: live appends share inodes) `--corpus` into the same temp dir the tools run from, then scan the copy once per tool (whole-copy `--scan DIR`, ~2 min total) or in batches. A torn copy is fine: both tools read identical bytes, the diff is valid, and the manifest sha256 of the copy bounds what "whole-corpus" meant. If per-file scans must stay, require the payload's own `files[].sha256` to equal the before-snapshot digest for both tools (that also catches A→B→A mutation inside the window, which before==after cannot see), and report coverage.

## D2 — `added_rows` is computed on the evidence-keyed multiset, so relabels are counted as new findings (code bug, not hypothetical)

`:220-233` computes additions as `new_evidence_rows - base_evidence_rows` where `_evidence_key` = `(file, line, class, rule, evidence)` and absent `evidence` normalizes to `"observed"` (`:127-129`, `:136-137`). Any row the new tool re-emits with `evidence: "lead"` where base said nothing (≡ observed) lands in `added_rows` as a *new* detection even though the (file, line, class, rule) detection is unchanged. It is not in `lost_rows` (that diff uses the evidence-free key `:211-217`), so the report shows a phantom addition with no matching loss. Concretely vs `1f7f995`: rule-B rows on unbound-callee literal argv (the round-19 harm shape) that tip re-emits as `lead` appear as "added package_query … lead" — the repair's own fix is presented as new coverage. The claim asks the diff to *class* every added row; a bucket whose members include not-added rows is a misclassification by construction.

Correction: `added = new_rows − base_rows` on the evidence-free key; a third bucket `relabeled` = multiset diff on evidence keys minus the true adds/loses (i.e. retained keys whose evidence, and — same mechanism — rule string or command text, changed). Evidence demotions (observed→lead) are semantic weakening of a retained row and must be listed even at count 0, not folded into additions.

## D3 — The join key `(file, line, class, rule)` manufactures loss on any relabel

TwMerge/RerunPrecision used the same key (R19 report `:89-90`), and it was safe then because class/rule vocabulary only *grew*. Round 20 changes semantics: TwVcsHelp's carve-outs and any rule-name normalization (e.g. `jj:git` granularity, `pacman:` op naming) can change `rule` on a retained detection → same line shows `lost {git:commit}` + `added {git:commit-dry-run-excluded}`; the claim's "loses 0" then fails on a rename, or worse — if L1 is tempted to treat a rename as acceptable and hand-waive it — the *next* real loss hiding under a rename gets waived too.

Correction: join first on `(file, line, tool_call_id)` (stable, both tools emit it, `tw-base.py:813` / `tw-r19.py:1598`), then classify each matched pair: `unchanged` / `rule_relabel` / `class_changed` / `evidence_relabel` / `command_text_changed` (the harness currently never compares `command`, so a different extraction rendered on the same key is invisible). `lost` = call ids present in base with no tip row at all. The `(file, line, class, rule)` multiset diff stays as a secondary view, not the loss oracle.

## What the diff must exclude or report separately

1. **Exclude nothing silently.** `unstable_files` (`:250-254`) is counts-only. Report the paths (or at minimum the session-root prefixes and share of corpus bytes) for `added_during_run`, `removed_during_run`, `changed_during_run`; D1 shows this set is exactly the live round-20 root. The receipt should name coverage: "5,714 files, N stable, excluded roots {MadoR20/: k files}". Round-19 did this; the current harness regresses it to three integers.
2. **Report separately: relabels** (D2/D3 buckets above): evidence observed→lead, rule renames, class moves, command-text changes on retained keys.
3. **Report separately: round-20 self-referential rows.** Added `observed` rows on `*R20*` transcripts are not the same population as added rows on the older corpus: (a) eval-code fixture generation is real `subprocess.run` text on real `eval` toolCalls → *true positives under the tool's contract but self-graded* (the tool "detects" code written to test it); (b) authorized `git -C /tmp/clone commit` in bash → true `vcs_write` (`GIT_WRITE` includes commit, `/tmp/cnd/tw-r19.py:138`; `git show`/`clone` are correctly unclassified); (c) `write`/`edit`/`task` arguments are never scanned (`tw-r19.py:1565-1576` only reads `bash`/`eval` toolCalls) — a bound that should be stated. Every added row in a `*R20*` file should get an adjudicated tag (`round20-fixture-codegen` / `authorized-tmp-vcs` / `genuine`), not just a group count.
4. **Report separately: parse-surface deltas.** The harness reads only `findings`. `unparsed_spawns`, `eval_unparsed`, `bash_calls`, `eval_calls` per stable file bound what "loses 0" can mean — a drop in `bash_calls`/`eval_calls` (call extraction changed) makes "lost 0" vacuous for the calls never read, and a rise in unparsed counters is the "unborn findings" channel (round-19's own evidence: +1 `eval_unparsed`, +1 `unparsed_spawns`, `RerunPrecision.md:124-135`). Diff all four counters; any rise is a flagged exception even when lost=0.
5. **Report separately: schema/version fields.** `_scan` (`:120`) hard-requires `schema == "mado-tripwire-verdict-v1"` — if the new verdict adds `observed_findings`/`lead_findings` under the same schema string it passes; if the schema string bumps, the whole new side errors to `could_not_evaluate` (fail-closed: acceptable, but the receipt then says nothing). Also `_scan` requires the verdict JSON to be the line *immediately after* `MADO_TRIPWIRE:` (`:113-117`); any stdout line between marker and payload is an error. Pin these expectations in the receipt.
6. **Exclude with a reason: nothing else.** `repo` is derived as `parents[3]` of the script path (`:142-143`) — correct in the lane, silently `git show`-failing if the script is run from a /tmp copy; `--base` must then name an absolute blob path. And note `files[]`/`findings[]` parse `errors="replace"` — a transcript with non-UTF8 bytes is scanned on replacement text by both tools (identical → harmless to the diff; state it).

## The comparison the claim actually needs (per-file vs per-line keys — resolved)

Both diffs, not one: **`9c54c56` vs final** is the registered no-harm axis (pre-harm reading restored) — require lost = 0 and every `added` group classed; expected adds: all `vcs_write`/`tool_install` rows, rule-B `lead` rows, new `observed` rows from helper/cross-cell resolution. **`1f7f995` vs final** isolates round-20's own delta — expect lost = 0 *and* the relabel ledger to contain exactly: rule-B ordinary rows → `lead`, `jj --help`/`git --dry-run` vcs_write rows → gone (these are not "lost vs 9c54c56"; they are "additions the harmed tool made that the repair declined to keep" — a distinct, named disposition, since a naive reader sees them as removals). That second diff is what proves the repair rather than the merge.

Per-file vs per-line: file-level counts (findings-per-file) are wrong — +2/−1 nets to a false pass. Per-`(file,line,class,rule)` multiset is necessary but not sufficient (D3). The loss oracle must be per-`tool_call_id` join; the multiset view reports multiplicity loss (two same-key rows → one, cf. round-19's key-increment observation) which a set-level diff misses.
