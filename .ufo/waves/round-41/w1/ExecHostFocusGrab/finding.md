# Which software on this host can bind the focus-grab protocol

Seat `ExecHostFocusGrab`, mado round 41 w1 (2026-10-25). Lane `mado-shokunin`.
Read-only host census. No compositor connection, no Wayland client, no input injection, no package transaction.

Question: **which software on this host can bind `hyprland_focus_grab_manager_v1` / `hyprland_focus_grab_v1`?**

Short answer: **only the compositor itself, and only as the server side.** Nothing installed on this host holds the
protocol on the client side. `hyprland_focus_grab_manager_v1` is advertised by `/usr/bin/Hyprland` and was *observed*
by the desktop portal, but the portal does not bind it, and no installed client — quickshell included, it is not
installed — carries the protocol name.

## 2. Result — the only binary on the host holding the protocol is the compositor

```
$ grep -o -a -E 'hyprland_focus_grab_manager_v1|hyprland_focus_grab_v1|hyprland_focus_grab|focus-grab|focus_grab' /usr/bin/Hyprland | sort | uniq -c
      2 hyprland_focus_grab_manager_v1
      2 hyprland_focus_grab_v1
```

`/usr/bin/Hyprland`, 16 099 784 bytes, sha256 `55da553be71222566ee73b973d2f56dbb9939044d8f22f81aa54b66c83f2f6d1`.

The binary carries both the generated interface structs and the interface name strings, i.e. the protocol is compiled in
as a **server** implementation:

```
$ strings -a /usr/bin/Hyprland | grep -n 'hyprland_focus_grab'

13442:hyprland_focus_grab_v1_interface
47799:hyprland_focus_grab_v1

```

The member-name strings sit in the generated message tables, so the request/event surface is present too:

```
$ strings -a /usr/bin/Hyprland | sed -n '47790,47815p'
...

add_surface
remove_surface
create_grab
```

(`cleared` = the event; `add_surface` / `remove_surface` = object requests; `create_grab` = the manager request.)

### 2b. The same protocol is installed as *server-side headers*, not client-side

```
$ grep -r -l -a -E 'hyprland_focus_grab|focus-grab' /usr/include
/usr/include/hyprland/protocols/hyprland-focus-grab-v1.hpp
/usr/include/hyprland/src/protocols/FocusGrab.hpp
```

- `/usr/include/hyprland/protocols/hyprland-focus-grab-v1.hpp` — 6306 bytes, 226 lines. Generated by
  `hyprwayland-scanner 0.4.6` (line 1). Declares
  `extern const wl_interface hyprland_focus_grab_manager_v1_interface;` (line 58) and
  `extern const wl_interface hyprland_focus_grab_v1_interface;` (line 59), and operates on `wl_resource`
  (`wl_resource_get_client`, `wl_resource_post_error`, line 91–107). **Server side.**
  `grep -c -E 'wl_proxy|wl_registry_bind'` on this header = **0** → there is no client-side binding code on disk.
- `/usr/include/hyprland/src/protocols/FocusGrab.hpp` — 2607 bytes, 78 lines; `class CFocusGrabProtocol : public IWaylandProtocol`,
  `class CFocusGrab` with `start()`, `finish(bool sendCleared)`, `commit()`, and a `CSeatGrab` member. This is Hyprland's
  in-tree manager that owns the seat grab. Header-only (no separate `.so`); the code is inside `/usr/bin/Hyprland`.
- Both paths live under `/usr/include/hyprland/`, and `/usr/share/licenses/hyprland` exists → the Hyprland package
  installed them. `[INFERENCE]` — `pacman -Qo` is forbidden by this seat's task, so ownership is by path, not by query.
- `hyprpm` (Hyprland plugin manager) is **not** installed (`command -v hyprpm` empty), so a third-party plugin route is
  not set up on this host. No `/usr/lib/hyprland` plugin directory exists.

## 5. False positive, excluded explicitly

`focus_grab` also matched GTK4 — not the protocol:

```
$ strings -a /usr/lib/libgtk-4.so.1.2400.1 | grep -n -B3 -A3 'focus_grab'
45422-gtk_window_destroy
45423-gtk_window_get_child
45424-gtk_window_set_child
45425:gtk_window_set_pointer_focus_grab
45426-gtk_widget_set_active_state
```

- The match is the substring `focus_grab` inside the GTK **widget-toolkit** name `gtk_window_set_pointer_focus_grab`,
  sitting in a contiguous block of `gtk_window_*` API names.
- It is not a dynamic symbol: `nm -D /usr/lib/libgtk-4.so.1.2400.1 | grep -c pointer_focus` = **0**.
- It is not in the installed headers: `grep -rn pointer_focus /usr/include/gtk-4.0/` = no output.
- GTK4 knows **no** Hyprland protocol: the `/usr/lib` sweep for `hyprland_` returns only
  `/usr/lib/xdg-desktop-portal-hyprland`, never a GTK library.

`/usr/bin/gtk4-rendernode-tool` (13 180 176 bytes) carries the same single string at line 42818 inside the **identical**
`gtk_window_*` name sequence (`get_child`, `set_child`, `set_pointer_focus_grab`, `widget_set_active_state`,
`set_focus_visible`). It does not even link libgtk-4 (`readelf -d | grep NEEDED` shows only `libgdk_pixbuf-2.0.so.0`),
so it embeds that GTK name table rather than binding anything. Both are excluded: **toolkit pointer-focus API,
unrelated to Wayland `hyprland_focus_grab_*`.**

`/usr/lib/libgtk-4.so.1.2400.1`, 13 048 760 bytes, sha256 `b1d66a913b737d2f5d6b0469e97d904a0da98802a3b929e20b4869aebc652c8b`.
(`/usr/lib64/libgtk-4.so.1.2400.1` is the same file through the `/usr/lib` symlink.)

- **No GTK4 / Qt / layer-shell helper carries it.** `libgtk-layer-shell.so.0.10.1` exists but does not match; no
  `libqt6waylandclient*` is installed at all.
- **No other compositor** is installed (only `Xwayland` alongside `Hyprland`); no alternative server could advertise it.
- **`wayland-info` cannot bind it.** `/usr/bin/wayland-info` exists but `strings -a /usr/bin/wayland-info | grep -c 'hyprland_'`

  it cannot `wl_registry_bind` this manager.
- **`hyprctl` does not use the protocol** (`strings /usr/bin/hyprctl` → no match); it speaks the compositor's own IPC socket.
- **Named desktop binaries that do not hold the string:** `walker`, `waybar`, `mako`, `makoctl`, `hyprlock`, `hypridle`,

## 7. What this does and does not establish

**Holding the string is evidence of capability, not of use.** `/usr/bin/Hyprland` containing
`hyprland_focus_grab_manager_v1` proves the compositor can *serve* the protocol; the journal line at
`fetch/xdph-journal.txt:117` proves it *did* advertise it on 2026-10-25. Neither proves any client ever bound it, and the
census says none can on this host today.

The reverse also holds: absence of the string in a binary is strong evidence that binary cannot bind the manager
(generated Wayland bindings are not constructed from runtime strings), but it is not a proof for code that builds
interface names dynamically — no such code was found, and no process was observed doing it.

### Limits

- Only mapped-file granularity was used for processes; anonymous `memfd`/JIT regions are not inspectable this way.
- `/opt/containerd` needed read-only `sudo -n` (root-only tree); no hits, gap closed.
- `/proc/*/maps` for other users' processes was unreadable (grep exit 2); the host's own session (uid 1000) was fully
  covered, which is where a desktop client would live.
- `grep -a` treats files as bytes, so a name split across a compressed or encrypted container would be missed; none of
  the matching candidates are such containers.
- No live probe was run: this seat may not open a Wayland connection, so "bindable at runtime" is inferred from compiled
  code, not exercised.
