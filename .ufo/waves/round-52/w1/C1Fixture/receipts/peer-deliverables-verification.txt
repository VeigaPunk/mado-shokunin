The peer's "HOLE_PROBES: 6/6 rejected" is confirmed.

The driver's scoring is a genuine check, not an exit-code check. Read from the source:

    value = fields.get(expect)
    ok = proc.returncode == 1 and value is not None and value not in ("0", "absent")
    print(... "REJECTED" if ok else "FALSE-GREEN")

A probe passes only when the counter exits 1 AND the expected field is present and
non-zero. An always-accept counter cannot satisfy it.

PROVEN BY SUBSTITUTION: the same driver was run against a counter that accepts every
ledger (a scratch stub that implements --ledger and always prints
`verdict=TARGET_MET`, exit 0):
  probe=ledger-self-pointer        exit=0 self_pointer=0  verdict=TARGET_MET -> FALSE-GREEN
  probe=row-self-pointer           exit=0 self_pointer=0  verdict=TARGET_MET -> FALSE-GREEN
  probe=peer-instrument-pointer    exit=0 bad_pointer=0   verdict=TARGET_MET -> FALSE-GREEN
  probe=cross-description          exit=0 generic_desc=0  verdict=TARGET_MET -> FALSE-GREEN
  probe=omnibus-pointer            exit=0 bad_pointer=0   verdict=TARGET_MET -> FALSE-GREEN
  probe=laundered-self-pointer     exit=0 self_pointer=0  verdict=TARGET_MET -> FALSE-GREEN
  HOLE_PROBES: 0/6 rejected
  exit=1

So the driver reports 6/6 against a correct counter and 0/6 against an always-accept
one: it discriminates in both directions.

Note the stub's own --ledger support matters. A counter that does not accept --ledger
exits 2 on every probe, which the driver scores as FALSE-GREEN (0/6, exit 1) - the right
verdict for the wrong reason, since the counters under comparison here all implement the
flag.
