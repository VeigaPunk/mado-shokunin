  replaced by print-only invocation of the same code path:

  id   Alacritty.desktop
  path /home/vgpnk/.local/share/applications/Alacritty.desktop   (not /usr/share/applications/...)
  Why, by rule (script lines of the pinned 44020-byte file):
    1. Order of list files — make_paths() lines 148-163: config dirs first (XDG_CONFIG_HOME then
       XDG_CONFIG_DIRS), per-desktop variant before the plain name (line 151 vs 153), then
       <data-dir>/xdg-terminal-exec/[<desktop>-]xdg-terminals.list (lines 159-162). First list that
       yields a usable id wins, so the user list (XDG_CONFIG_HOME/xdg-terminals.list, line 3) supplies
       the id before the system list is consulted at all.
    2. Order of application dirs — make_paths() line 168 prepends each dir, iterating
       XDG_DATA_HOME then XDG_DATA_DIRS, so XTE__APPLICATIONS_DIRS ends up in ASCENDING preference:
       /usr/share, /usr/local/share, then /home/vgpnk/.local/share last.
    3. Duplicate id resolution — find_entry_paths() line 780-782: "Entries are checked in ascending
       order of preference, so use last found if duplicate", then
       `alias "$xte__entry_id"="xte__entry_path='$xte__entry_path'"`. The user dir is scanned last, so
       its alias overwrites the system one; the id Alacritty.desktop therefore resolves to the user path.
    4. Explicitly listed ids are not subject to DE show-in limits (comment at find_entry() line 1057),
       and find_entry() line 1060 walks ${XTE__ENTRY_IDS} before //fallback_start//, so the config-list
       hit is tried first.
  Evidence chain for (1)-(4) is [3] (only the user file was opened), [4] (only the user list names it),
  [5] (the user-only keys show up in the composed command) and [7a] (removing the user data dir flips
  the path to the system file).
