## 2. Upstream Output-Management Implementation (`zwlr_output_manager_v1`)

### 2.1 Registration and Sandbox Privilege
- **Registration point:** `src/managers/ProtocolManager.cpp:195`:
  ```cpp
  PROTO::outputManagement = makeUnique<COutputManagementProtocol>(&zwlr_output_manager_v1_interface, 4, "OutputManagement");
  ```
- **Interface Version:** Advertised at version **4**.
- **Sandbox Gate:** In `ProtocolManager.cpp:358-403`, `CProtocolManager::isGlobalPrivileged()` defines `ALLOWED_WHITELIST`. `PROTO::outputManagement` is **absent** from `ALLOWED_WHITELIST`. Consequently:
  ```cpp
  // Compositor.cpp:263-267
  static bool filterGlobals(const wl_client* client, const wl_global* global, void* data) {
      if (!PROTO::securityContext->isClientSandboxed(client))
          return true;
      return !g_pProtocolManager || !g_pProtocolManager->isGlobalPrivileged(global);
  }
  ```
  `zwlr_output_manager_v1` is classified as **privileged** and is filtered out for sandboxed clients. Only unsandboxed clients receive global advertisement.
- **Teardown:** Explicitly reset during protocol manager destruction (`ProtocolManager.cpp:305`: `PROTO::outputManagement.reset()`).

### 2.2 Head & Mode Advertisement Lifecycle
- **Enumeration:** On client bind (`COutputManagementProtocol::bindManager`), a `COutputManager` is instantiated. It iterates active outputs via `State::monitorState()->allMonitors()` and emits `makeAndSendNewHead(m)` (`OutputManagement.cpp:35-39`).
- **Head Metadata:** `COutputHead::sendAllData()` sends name, description, physical size, enabled state, position, transform, scale, make/model/serial (for version >= 2), and adaptive sync state (`ZWLR_OUTPUT_HEAD_V1_ADAPTIVE_SYNC_STATE_*` for version >= 4) (`OutputManagement.cpp:125-149`).
- **Mode Objects:** Modes are emitted as distinct `COutputMode` objects (`OutputManagement.cpp:153-162`), communicating pixel size, refresh rate in mHz, and preferred flag.
- **Serial Batching:** The configuration snapshot is sealed by `sendDone()` with serial generated by `wl_display_next_serial(g_pCompositor->m_wlDisplay)` (`OutputManagement.cpp:92-94`).

### 2.3 Critical Implementation Limits: Test Stub vs Apply Override
1. **The `test` Request is a Stub:**
   When a client issues `zwlr_output_configuration_v1.test`:
   ```cpp
   // src/protocols/OutputManagement.cpp:343-346
   bool COutputConfiguration::applyTestConfiguration(bool test) {
       if (test) {
           LOGM(Log::WARN, "TODO: STUB: applyTestConfiguration for test not implemented, returning true.");
           return true;
       }
   ```
   Hyprland 0.56.2 **unconditionally returns `true`** and fires `sendSucceeded()` without checking whether modes, timings, bandwidth, CRTC allocations, or connectors can actually be supported by DRM/KMS.
2. **The `apply` Request Lifecycle:**
   When a client issues `zwlr_output_configuration_v1.apply`:
   - It populates `m_owner->m_monitorStates[PMONITOR->m_name] = newState;` with committed properties (mode, custom mode, position, transform, scale, adaptive sync, enabled).
   - It calls `Config::monitorRuleMgr()->scheduleReload();` (`OutputManagement.cpp:419`).
   - It registers the configuration object in `m_pendingConfigurationSuccessEvents` and calls `m_owner->sendDone()`.
   - In `MonitorRuleManager.cpp:44-79` (`CMonitorRuleManager::get`), the compositor intercepts monitor configuration through `applyWlrOutputConfig()`:
     ```cpp
     const auto CONFIG = PROTO::outputManagement->getOutputStateFor(PMONITOR);
     if (!CONFIG) return rule;
     // Overrides rule.m_disabled, rule.m_resolution, rule.m_refreshRate,
     // rule.m_offset, rule.m_transform, rule.m_scale, rule.m_vrr
     ```
   - When the rule manager reloads its state (`m_events.stateReloaded`), `COutputManagementProtocol` receives the event, calls `updateAllOutputs()`, and finally sends `config->m_resource->sendSucceeded()` via `sendPendingSuccessEvents()` (`OutputManagement.cpp:602-605, 661-672`).
3. **Serial Verification Gap:**
   When the client creates a configuration via `create_configuration(id, serial)`, the provided serial is received into logging but is **not validated** against the current compositor serial before allowing head mutations or apply.
4. **Parameter Validation:**
   - Scale must satisfy `0.1 <= scale <= 10.0`; else `ZWLR_OUTPUT_CONFIGURATION_HEAD_V1_ERROR_INVALID_SCALE`.
   - Transform must be `0 <= transform <= 7`; else `ZWLR_OUTPUT_CONFIGURATION_HEAD_V1_ERROR_INVALID_TRANSFORM`.
   - Dimensions and refresh must be positive; else `ZWLR_OUTPUT_CONFIGURATION_HEAD_V1_ERROR_INVALID_CUSTOM_MODE`.
   - Attempting to set an already-committed property on a head raises `ZWLR_OUTPUT_CONFIGURATION_HEAD_V1_ERROR_ALREADY_SET`.

## 3. Upstream Color-Management Implementation (`wp_color_manager_v1`)

### 3.1 Conditional Registration and Version Negotiation
- **Registration point:** `src/managers/ProtocolManager.cpp:234-235`:
  ```cpp
  static const auto PENABLECM = CConfigValue<Config::INTEGER>("render:cm_enabled");
  static const auto PDEBUGCM  = CConfigValue<Config::INTEGER>("debug:full_cm_proto");
  static const auto PCMV1_2   = CConfigValue<Config::INTEGER>("experimental:wp_cm_1_2");
  ...
  if (*PENABLECM)
      PROTO::colorManagement = makeUnique<CColorManagementProtocol>(&wp_color_manager_v1_interface, *PCMV1_2 ? 3 : 1, "ColorManagement", *PDEBUGCM);
  ```
- **Support-limits for Registration:**
  - If `render:cm_enabled` is `0`, `wp_color_manager_v1` is **not registered at all** (`PROTO::colorManagement` is null).
  - If `experimental:wp_cm_1_2` is `1`, version **3** is registered; if `0`, version **1** is registered.
  - `debug:full_cm_proto` toggles debug features in `CColorManagementProtocol`.
- **Sandbox Whitelist Status:**
  In `ProtocolManager.cpp:399`, `PROTO::colorManagement ? PROTO::colorManagement->getGlobal() : nullptr` **is included** in `ALLOWED_WHITELIST`. Sandboxed clients can see and bind `wp_color_manager_v1`.

### 3.2 Advertised Features vs Upstream Implementation Limits
In `CColorManager::CColorManager` (`ColorManagement.cpp:16-72`):
1. **Always Advertised Features:**
   - `PARAMETRIC`
   - `SET_PRIMARIES`
   - `SET_LUMINANCES`
   - `WINDOWS_SCRGB`
   - `SET_MASTERING_DISPLAY_PRIMARIES`
   - `EXTENDED_TARGET_VOLUME`
   - Version >= 3 conditional: `WINDOWS_BT2100`
2. **ICC Profile Gating (Strict Limit):**
   - ICC support (`WP_COLOR_MANAGER_V1_FEATURE_ICC_V2_V4` and `WP_COLOR_MANAGER_V1_FEATURE_SET_TF_POWER`) is only advertised when `m_debug` (`debug:full_cm_proto`) is true (`ColorManagement.cpp:28-31`).
   - If a client calls `create_icc_creator` when debug is disabled:
     ```cpp
     // ColorManagement.cpp:163-165
     if (!PROTO::colorManagement->m_debug) {
         r->error(WP_COLOR_MANAGER_V1_ERROR_UNSUPPORTED_FEATURE, "ICC profiles are not supported");
         return;
     }
     ```
3. **Surface Render Intent (Strict Limit):**
   - The manager advertises `WP_COLOR_MANAGER_V1_RENDER_INTENT_PERCEPTUAL` (and in debug mode, relative, saturation, absolute).
   - However, on surface attachment (`CColorManagementSurface::setSetImageDescription`, `ColorManagement.cpp:316-319`):
     ```cpp
     if (render_intent != WP_COLOR_MANAGER_V1_RENDER_INTENT_PERCEPTUAL) {
         r->error(WP_COLOR_MANAGEMENT_SURFACE_V1_ERROR_RENDER_INTENT, "Unsupported render intent");
         return;
     }
     ```
     **Perceptual is the ONLY supported render intent.** Passing any other intent results in a fatal protocol error.
4. **Surface Image Descriptions:**
   Surfaces default to `getDefaultImageDescription()` (sRGB). Clients can bind parametric or Windows scRGB / BT2100 descriptions.

### 3.3 Output Color Management & The Display HDR Boundary
- **Output Image Description:**
  Clients obtain a `wp_color_management_output_v1` from `get_output`, then call `get_image_description` (`ColorManagement.cpp:254-273`).
  The description is populated directly from `m_output->m_monitor->m_imageDescription`.
- **Monitor Image Description Determination:**
  In `src/output/Monitor.cpp:542-650` (`CMonitor::applyCMType`):
  Supported compositor modes include `CM_SRGB`, `CM_WIDE`, `CM_DCIP3`, `CM_DP3`, `CM_ADOBE`, `CM_EDID`, and `CM_HDR`.
- **Display HDR Capability Boundary:**
  In `src/output/Monitor.cpp:2412-2417`:
  ```cpp
  bool CMonitor::supportsHDR() {
      switch (m_supportsHDR) {
          case -1: return false;
          case 1: return true;
          default: return m_output->parsedEDID.hdrMetadata.has_value() ? m_output->parsedEDID.hdrMetadata->supportsPQ : false;
      }
  }
  ```
  And `CMonitor::inHDR()` checks `m_output->state->state().hdrMetadata.hdmi_metadata_type1.eotf == 2` (`Monitor.cpp:2448-2450`).
- **Critical U5 Finding (Protocol Advertisement != Display HDR):**
  Advertised presence of `wp_color_manager_v1` version 3 does **not** indicate that HDR display output is operational. Advertisement indicates only that the compositor compiled and enabled the protocol endpoint (`render:cm_enabled = 1`, `experimental:wp_cm_1_2 = 1`). Whether an attached physical display supports or activates HDR depends strictly on monitor EDID parsing (`parsedEDID.hdrMetadata->supportsPQ`) and DRM KMS connector state.
- **Preferred Image Description Change Detection Stub:**
  In `src/Compositor.cpp:984-987`:
  ```cpp
  bool CCompositor::shouldChangePreferredImageDescription() {
      Log::logger->log(Log::WARN, "FIXME: color management protocol is enabled and outputs changed, check preferred image description changes");
      return false;
  }
  ```
  Hyprland 0.56.2 stubs dynamic preferred image description renegotiation, logging a warning and returning `false`.

## 5. U5 Coverage & Operability Boundaries

Connecting upstream source findings directly to milestone U5:
1. **Output Management Boundary (`zwlr_output_manager_v1`):**
   - Pinned Hyprland 0.56.2 advertises version 4 to unsandboxed clients.
   - Calling `test` does **not** test hardware validity or KMS atomic test-only commitments; it is a no-op stub that always reports success.
   - Calling `apply` overrides the compositor's monitor rule table in `CMonitorRuleManager`, dynamically replacing configuration file values until compositor restart or subsequent overrides.
2. **Color Management Boundary (`wp_color_manager_v1`):**
   - Advertised version is decoupled from display hardware: version 3 advertisement is governed by `render:cm_enabled` and `experimental:wp_cm_1_2`.
   - Surface color management is restricted to perceptual intent. Passing any other intent raises a protocol error.
   - ICC profiles are rejected with `WP_COLOR_MANAGER_V1_ERROR_UNSUPPORTED_FEATURE` unless `debug:full_cm_proto` is enabled.
   - Advertisement of `wp_color_manager_v1` must never be conflated with HDR display capability.
3. **No Feature Exercise Claim:**
   In compliance with C1/C2 constraints, this investigation exercises no live compositor mutation or protocol client requests; it establishes the structural boundaries and implementation limitations directly from the authoritative pinned upstream source.
