Axes: coverage (C2) and operability (C1). Compared the frozen predicates in `claims.md` and `registration.md` to the pre-data control specs/receipts, and checked committed revision strings and exit-code evidence in the base receipts. The gate draft's alternate `LEDGER:` schema is expressly distinguished from frozen C1's `C1_R51:` schema; do not treat that gate receipt alone as proof of the frozen command output.

Base command evidence: `.ufo/waves/round-51/w1/ExecLedgerCounter/receipts/base-and-setup.txt` lines 1–5 records exact base `6ca8c559a4a3d6d361101592116eea2bc7452437`, `ledger=absent population=79`, `TARGET_MISSED`, exit 1. This satisfies the frozen red-before clause. The fixture revision IDs and the `--rev` versus worktree control are in the C1 spec §§2–3 and `expected.txt` lines 25–30, 60–69. Fixture commits are not reproducible hashes by design; the control tree was removed, so this audit cannot independently resolve those synthetic IDs now. They are not lane revisions. C1's own spec documents unresolved predicate edges (duplicate-row representation and literal meaningfulness of descriptions/pointers), but these are explicit limitations rather than failures of the stated control set.

## C2 — PASS for recorded expected misses; control-spec wording discrepancy
`controls-c2/spec.md` table lines 16–37 defines seven controls. It explicitly states ctl-a/ctl-b do not isolate (c): their copied historical metadata also fail (b),(d); ctl-a2/ctl-b2 are isolating variants that preserve body bytes and arrange (a),(b),(d) pass, leaving (c) alone. `expected.json` records those vectors and rc=1 for all seven controls; `receipts/summary.txt` lines 6–14 records every control `TARGET_MISSED`, both probe and counter rc=1, `controls=7 matched=7 mismatched=0`. The C2 base receipt `w1/ExecCounterC2/receipt-base.txt` lines 1–11 records the exact frozen base revision, clauses_met=0/admitted=0/1/TARGET_MISSED and exit 1. This matches the frozen base clause. The C2 base receipt also pins counter SHA256 `ebe39e1183375e0fb102124057eafecc9a21bdfc330c04ceb03759093d10e6dd`; `controls-c2/spec.md` lines 68–74 reports the same hash and notes counter drift before final receipts.

Concrete spec inconsistency: `expected.json` ctl-a2/ctl-b2 claim `max_overlap` 0.993/0.992 (lines 19–48), and the prose table in `spec.md` lines 76–84 repeats those values, but `receipts/summary.txt` lines 7 and 9 reports 0.9747 and 0.9719 respectively. These are all below the 30% threshold? No: each is far above threshold, so predicate verdict is unchanged; the recorded overlap *value* is inconsistent, weakening exact control evidence. The report should cite summary as measured receipt and label expected/spec figures stale or erroneous. This is a documentation/evidence discrepancy, not a false expected MISS.
