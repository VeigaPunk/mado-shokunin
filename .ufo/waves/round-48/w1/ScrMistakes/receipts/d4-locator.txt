38:6. Exec-arg composition. The option loop (xdg-terminal-exec:1224-1321) consumes leading options: `--` and `-e` (or whatever the entry's exec argument is) end option processing and are dropped (xdg-terminal-exec:1226-1235), `--app-id=`, `--title=` and `--dir=` are split at their `=` (xdg-terminal-exec:1236-1259), `--hold` and `--test` set flags (xdg-terminal-exec:1260-1271), the print flags of step 7 set `XTE__PRINT_DATA`, an unknown `-*` option is discarded (xdg-terminal-exec:1317-1320) and the first non-option ends the parse (xdg-terminal-exec:1313-1316). The command is then assembled by repeated front-prepending (xdg-terminal-exec:1387-1452), one `set -- "$XTE__EXECARG" "$@"` (xdg-terminal-exec:1389) per group, in the order exec argument, hold, dir, title, appid, and finally the entry's own `Exec` words; because every group prepends, the last prepend lands first: [Exec…] [AppId] [Title] [Dir] [Hold] [ExecArg] [command…]. Each key ending in `=` fuses its value into the same argument (xdg-terminal-exec:1403); a key without a trailing `=` yields two arguments (xdg-terminal-exec:1407, 1422, 1437). A requested `--title=`/`--app-id=`/`--hold` that the entry has no key for is dropped silently (xdg-terminal-exec:1396-1398, 1426-1428, 1441-1443), and a requested `--dir=` without `X-TerminalArgDir` is applied with `cd` just before exec instead (xdg-terminal-exec:1494-1497). The exec argument is only prepended when at least one command word follows and the entry's exec argument is non-empty (xdg-terminal-exec:1388) - an empty `TerminalArgExec` therefore produces no argument at all, which is the documented way to say "no exec argument". Everything is then exec'd in the same process (xdg-terminal-exec:1499): the terminal replaces the resolver, it is not forked behind it (README.md:218).
43:The cache is not part of the selection chain; it is a shortcut in front of it, and it is on by default (`XTE__CACHE_ENABLED=${XTE_CACHE_ENABLED-true}`, xdg-terminal-exec:1172). Unless that variable is falsy the resolver always *tries* to read the file first (xdg-terminal-exec:1179) and, on a hit, skips steps 1-5 entirely - the README states it plainly (`Valid cache bypasses reading of any other file.`, README.md:300-301 - the quote spans two lines of the pin). The key is an md5 (xdg-terminal-exec:179-215) over the literal `4` (the format version, xdg-terminal-exec:194), `$XDG_CURRENT_DESKTOP` and the `ls -LRl` listing of every config and applications path (xdg-terminal-exec:200), so touching any list file, desktop entry or directory in those trees invalidates it. The file holds two-digit-free positional records: ten lines (hash, command, entry path, entry id, action, execarg, appidarg, titlearg, dirarg, holdarg) followed by the command words joined by ASCII Unit Separator and terminated by Record Separator + `END_OF_EXEC_USEP` (xdg-terminal-exec:217-298, the reader; 300-340, the writer). A cache is accepted only when the recomputed hash matches *and* the cached command is still on `PATH` (xdg-terminal-exec:274). Saving happens on a non-cached run that gets past the print bail-out - `--print-cmd`, `--test` or a real launch - forked into the background (`save_cache "$1" &`, xdg-terminal-exec:1455-1458), creating `$XDG_CACHE_HOME` if needed (xdg-terminal-exec:303) and writing with `umask 0077`; a run with only `--print-id`/`--print-path` exits before it (xdg-terminal-exec:1378-1384) and writes nothing. The newline guard at xdg-terminal-exec:312-317 compares the whole concatenation of hash, command and arguments with a lone newline, so it fires only when that concatenation is exactly a newline, not when one argument merely contains one. Two consequences for anyone modelling this: a warm cache hides the list files from the run entirely, and a `--print-cmd` probe refreshes the cache it was meant to observe - both why a tool that must answer "why" models a cold cache, and why every probe of this round pointed `XDG_CACHE_HOME` into scratch.
