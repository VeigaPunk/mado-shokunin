## Findings the C2 entry can cite

1. **RMLVO → KcCGST entry chain.** `xkb_keymap_new_from_names` (`src/keymap.c:183`) forwards to the v2 form (`:187`),
   empty names are filled from build defaults (`src/context-priv.c:187`, `:193`; defaults are meson options,
   `meson.build:194-203`), and components come from `xkb_components_from_rules_names` (`src/xkbcomp/xkbcomp.c:157` →
   `src/xkbcomp/rules.c:2111`). Failure there prints `Couldn't look up rules …` (`xkbcomp.c:106`).
2. **Why a bad *option* is only a warning while a bad *layout/variant* kills the compile.** A rule row applies only if
   it fills exactly the section's columns (`rules.c:1481`); `*` matches the empty value for model/options but not for
   layout/variant (`rules.c:1504`, `:1140`); unmatched values are logged at **error** level and compilation continues
   (`rules.c:2062-2063`, id **XKB-595** = `messages-codes.h:150`). `rules/evdev` has a **model** catch-all
   (`fetch/host/rules-evdev:59` `* = evdev`), so `--model nope` produces *no message at all* (measured: rc 0, empty
   stderr) — the "unknown model: rc 0" line in the ticket is right for a subtler reason than "warning suppressed".
   A wrong layout/variant instead reaches the symbols include: **XKB-338** `Couldn't find file` (`include.c:355`,
   `messages-codes.h:116`), **XKB-661** `Couldn't process include statement` (`include.c:501`,
   `messages-codes.h:162`), and the terminal **XKB-822** `Failed to compile keymap` (`xkbcomp.c:62`,
   `messages-codes.h:190`); `xkbcli` then sets `EXIT_FAILURE` (`tools/compile-keymap.c:521`).
3. **Include-path order** is exactly the ticket's: `$XDG_CONFIG_HOME/xkb` (`context.c:257`, kept even when empty) →
   `$HOME/.config/xkb` only if unset (`:264`) → `$HOME/.xkb` (`:272`) → `XKB_CONFIG_EXTRA_PATH` / built-in
   `<sysconfdir>/xkb` (`:279`, `:97`) → `XKB_CONFIG_ROOT` / xkeyboard-config data dir (`:317`, `:236`), the last two
   baked from meson (`meson.build:179`, `:192`, root from the xkeyboard-config pkg at `:116`). Host proof at INFO level:
   3 `Include path failed` user paths then `Include path added: /usr/share/xkeyboard-config-2`.
   Also: the rules file itself is `<rules>` bracketed by optional `<rules>.pre`/`.post` partials found in **every**
   include path (`rules.c:2000-2006`) — a mechanism the C2 entry should mention, because a user-local `rules/evdev`
   silently *extends* the system one.
4. **Multi-layout/variant alignment** (`rules.c:520-533`, measured in `receipts/layout-alignment.txt`): more layouts
   than variants → **log_warn** (invisible at the default level, visible at `XKB_LOG_LEVEL=warning`) and variants padded
   with empties, so one variant attaches to layout 1 only (`us,br` + `nodeadkeys` → `us(nodeadkeys)` → XKB-661 because
   `symbols/us` has no `nodeadkeys` in 2.48). Fewer layouts than variants → **log_err** (always printed) but **rc 0**:
   the surplus variant is truncated and `br(nodeadkeys)` compiles.
5. **Host layout receipt (read-only).** `~/.config/hypr/input.conf:10-11` = `br` + `compose:caps`;
   `xkbcli compile-keymap --layout br --options compose:caps` → rc 0, 73079-byte keymap, sha256 `efd487a3…`, empty
   stderr, symbols set name `pc_br_inet(evdev)_compose(caps)`, i.e. KcCGST `pc+br+inet(evdev)+compose(caps)` from
   `rules/evdev:175` (`* * = pc+%l%(v)`), `:378` (`* = +inet(evdev)`) and `:570` (`compose:caps = +compose(caps)`).
6. **What the host's `rules/evdev` is built from.** Not a shipped file: `rules/meson.build:21-36` runs
   `python3 -m rules.generator rules --ruleset evdev --version v2 [--compat]`, and `rules/evdev.xml` is a byte copy of
   `rules/base.xml` (`rules/meson.build:49-52`). Byte-exact confirmation on this host: rendering the tag's
   `rules.in` with the tag's generator **with `--compat`** gives sha256
   `0cc48ee1279d91045fe2cf092ee5a0744cbee1c02bd164f02871d13140d12132`, identical to `/usr/share/xkeyboard-config-2/rules/evdev`
   (31520 bytes); without `--compat` it differs (`ab627a66…`, 190 changed lines). `verify.sh` §4 re-derives this from
   the pins on every run.

## Risks / corrections to the ticket's shorthand

- **XKB-595 is the option/model warning; the include failures are XKB-338 and XKB-661; the terminal line is XKB-822.**
  `--rules nope` emits *both* XKB-338 (`Couldn't find file "rules/nope"`) and a summary `[XKB-595] Cannot load XKB
  rules "nope"` — so "rules: exit 1 'Couldn't find file symbols/zz'" is right about rc and text but the id belongs to the
  file lookup, not to the rules load.
- **Unknown model is not merely "dropped with a warning"**: no message is printed at all, because the model catch-all
  row matched. If the knowledge entry writes "unknown model: warning", it will be wrong on stderr, right on rc.
- **`us(nodeadkeys)` does not exist in xkeyboard-config 2.48** (`grep -c nodeadkeys symbols/us` = 0), while
  `br(nodeadkeys)` does (`symbols/br:47`). Any C2 example using `nodeadkeys` for `us` must expect rc 1.
- **The padding warning is `log_warn`**, i.e. absent from default `xkbcli` output. A verifier that asserts "rc 1 and a
  warning about layout/variant count" at default level will fail for the wrong reason.
- **Source availability:** the freedesktop GitLab raw path for libxkbcommon returns a GitLab *sign-in page*
  (`<title>Sign in · GitLab</title>`), so the GitHub mirror is what is pinned (cross-check of intent: pinned
  `meson.build:4` declares `version: '1.13.2'`; the tag ref is annotated tag object `322bf223…`). xkeyboard-config's
  GitLab raw paths serve plain files and match the installed package.
- **Generation needs more than `rules/`**: the generator resolves every option to an existing `xkb_<section>` header
  (`rules/generator/options.py:60`), so it needs the component trees. `verify.sh` borrows the installed
  `/usr/share/xkeyboard-config-2/{symbols,keycodes,types,compat,geometry}` read-only (override with `XKB_HOST_TREE`) and
  recreates the tag's 8 legacy symbol symlinks (`caps→capslock`, `esperanto→epo`, `grp→group`, `japan→jp`,
  `korean→kr`, `lv2→level2`, `lv3→level3`, `lv5→level5`), which the Arch package does **not** ship (142 installed files
  vs 151 in the tag). Stated because it means "byte-identical" here is proven over the *pinned renderer + the shipped
  component tree*, not over a fully pinned copy of every xkeyboard-config file.
- Not done (out of seat scope): `corpus/knowledge/xkb-keymap-compile-r48.md`, `SOURCES` rows S340+, `hyprland-input-devices-r46.md`
  edits. I cite the held Hyprland ground only: `corpus/knowledge/hyprland-input-devices-r46.md:42` (S318), `:43` (S319),
  join row `:24`, open limit `:69`.
