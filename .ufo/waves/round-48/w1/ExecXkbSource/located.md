## Note on `XKB-595` vs `XKB-338`

(`Couldn't find file`) and **XKB-661** (`Couldn't process include statement`), and the terminal line is **XKB-822**
(`Failed to compile keymap`, C11/C12) — the ticket's phrase "Failed to compile keymap" is that 822 message, not a
separate id.

## Verification

`./verify.sh` (read-only; needs `sha256sum`, `cmp`, `grep`, `sed`, and `python3` for §4; `xkbcli` for the live part):
`receipts/verify-output.txt` — **passed=125 failed=0**.

It checks, from this directory only:
1. every `fetch/PINS.txt` digest (32 pinned entries);
2. the host snapshots against the pins (`symbols/br`, `rules/base.xml`, `rules/base.extras.xml`,
   `rules/evdev.xml` == `rules/base.xml`);
3. each locator above: `uniq1 file pattern line` where the pattern occurs exactly once, `at file line pattern`
   where it legitimately repeats — so a shifted or re-tagged file fails the row it backs;
4. the generation chain of §F (rebuild `rules/evdev` from the pinned generator + `rules.in` over the installed
   component tree, `cmp` against the host file, and the same run without `--compat` must differ);
5. the live receipts: the 73079-byte keymap digest and its `xkb_symbols "pc_br_inet(evdev)_compose(caps)"` name, plus a
   fresh `xkbcli compile-keymap` for all rows of the live table (rc and stderr token), the log-level asymmetry of
   §E (the padding warning exists only at `XKB_LOG_LEVEL=warning`), and the INFO-mode include-path census of D12/D13.

What is **not** reproduced anywhere in this seat: launching a compositor, writing XKB files, or touching
`~/.cache`/compositor state. The `xkbcli` runs are `compile-keymap` only, stdout discarded or kept as a receipt.
