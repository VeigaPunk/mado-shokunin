## Answers

1. **Context flags.** Every Hyprland keymap build creates its context with `XKB_CONTEXT_NO_FLAGS`: IKeyboard.cpp:75 (setKeymap, the per-keyboard keymap), IKeyboard.cpp:226 (translation state), KeybindManager.cpp:311 (bind-resolution translation state), protocols/VirtualKeyboard.cpp:75 (client-supplied keymap, `new_from_string`, no names). No other xkb_context_new in src/ (grep over the whole commit tarball). NO_FLAGS = default include paths ON, environment names ON, secure_getenv ON: context.c:505-506,523 (`use_environment_names = !(flags & NO_ENVIRONMENT_NAMES)`, `pending_default_includes = !(flags & NO_DEFAULT_INCLUDES)`), flag doc xkbcommon.h:791,801,803. So the XKB_CONTEXT_NO_ENVIRONMENT_NAMES flag is NOT used.
2. **Five names -> keymap.** Config values input:kb_rules/model/layout/variant/options (per-device override via getDeviceString) are read at InputManager.cpp:1226-1231, stored and passed as `IKeyboard::SStringRuleNames{LAYOUT, MODEL, VARIANT, OPTIONS, RULES}` to `setKeymap` (InputManager.cpp:1286). setKeymap fills `xkb_rule_names` with `.c_str()` of each (IKeyboard.cpp:67-73; empty std::string -> "", never NULL) and calls `xkb_keymap_new_from_names2(CONTEXT, &XKBRULES, XKB_KEYMAP_FORMAT_TEXT_V2, XKB_KEYMAP_COMPILE_NO_FLAGS)` (IKeyboard.cpp:99). It uses _names2, format TEXT_V2. If kb_file is set, `xkb_keymap_new_from_file` is tried first (IKeyboard.cpp:87-96) and names are used only if that yields null (:98). Inside libxkbcommon: xkb_keymap_new_from_names2 (keymap.c:141) -> `xkb_context_sanitize_rule_names` (keymap.c:171; context-priv.c:187-225) -> text_v1_keymap_new_from_names (xkbcomp.c:142) -> `xkb_components_from_rules_names` (xkbcomp.c:157, RMLVO -> KcCGST) -> XkbFileFromComponents -> compile (xkbcomp.c:177-193).
   - **Sanitize semantics that matter for the entry** (context-priv.c): empty rules/model -> default (env XKB_DEFAULT_RULES/_MODEL else build default; context-priv.c:192-199,134); empty layout -> default layout AND default variant, any caller variant discarded with a warning (:202-217); options is replaced by the default only when NULL (:219) - Hyprland passes "" so options are never taken from XKB_DEFAULT_OPTIONS. Build defaults come from meson_options.txt (default-rules 'evdev', default-model 'pc105', default-layout 'us', variant/options '', meson_options.txt:32-59, receipt-computed). Whether the Arch build keeps those defaults is [INFERENCE] (the host's xkbcli printing evdev/pc105 on an all-empty compile would confirm it; not run here).
3. **Error path.** Failure of names2 returns NULL (xkbcomp.c:159-166 logs "Couldn't look up rules ..." and returns false; keymap.c:173-176 unrefs and returns NULL). Hyprland then (IKeyboard.cpp:101-116): queues an ErrorOverlay "Invalid keyboard layout passed. ( rules: ..." (:102), logs, zeroes XKBRULES (:107), resets stored names to layout "us" and the rest empty (:109-113), and retries names2 with the zeroed struct (:115) - that retry goes through sanitize, so the empty rules/model/variant/options become libxkbcommon defaults and layout empty -> default layout (env XKB_DEFAULT_LAYOUT, else us). Rows S318/S319 already hold the stored-names half; this entry adds only the retry-through-sanitize fact [new, S340..]. The bind-resolution translation state (KeybindManager.cpp:319-329) has its OWN fallback: all-zero rules, a separate "[Runtime Error]" overlay (:320), no `us` string written. The per-keyboard translation state (IKeyboard.cpp:226-290) is built from layout/model/variant ONLY with rules=""/options="" (:236-247) and falls back twice: model+variant dropped (:251-253), then layout "us" (:256-259) - so **kb_options never reach the translation state** and a failing variant degrades silently there while the real keymap (:99) takes the overlay + "us" path.
4. **Do XKB_CONFIG_ROOT / XDG_CONFIG_HOME / ~/.config/xkb apply to the compositor? Yes.** NO_FLAGS means libxkbcommon appends its default includes lazily on the first include/rules lookup (context.c:523 comment, context-priv.c:34-43 `xkb_context_init_includes`), reading env via secure_getenv (context-priv.c:24-25; identical to getenv for a non-setuid process, [INFERENCE] Hyprland is not setuid). Order, context.c:243-337 (v1.13.2):
   1. `$XDG_CONFIG_HOME/xkb` if XDG_CONFIG_HOME is set (even if empty), ELSE `$HOME/.config/xkb` (context.c:254-269) - the HOME fallback is an else-if: with XDG_CONFIG_HOME set, $HOME/.config/xkb is NOT added.
   2. `$HOME/.xkb` if HOME is set (context.c:271-277).
   3. extra path: env XKB_CONFIG_EXTRA_PATH else build default (context.c:92-97,279-280); the default is `prefix/sysconfdir/xkb` (meson.build:152-154) = /etc/xkb on a standard /usr, /etc build [INFERENCE; host-side confirmation is the xkbcli include-path report in the task facts].
   4. extension directories (versioned then unversioned; context.c:282-314), guarded by HAVE_XKB_EXTENSIONS_DIRECTORIES (build option, not verified for the Arch build).
   5. system root: env XKB_CONFIG_ROOT else DFLT_XKB_CONFIG_ROOT (context.c:228-237,316-319); if the root cannot be added, DFLT_XKB_LEGACY_ROOT is tried (context.c:330-337).
   Each candidate must stat as a directory and pass R_OK|X_OK or it is dropped as "Include path failed" (context.c:35-76, info-level log). If NO default path could be added: "Failed to add any default include path" (context-priv.c:37-41) and the lookup fails.
   Hyprland itself sets none of XKB_*/XDG_CONFIG_HOME/HOME: its setenv calls (Compositor.cpp:208,417,419; main.cpp:65-69) touch only HYPRLAND_*, WAYLAND_DISPLAY, XDG_CURRENT_DESKTOP, XDG_BACKEND, XDG_SESSION_TYPE, _JAVA_AWT_WM_NONREPARENTING, MOZ_ENABLE_WAYLAND. The hyprlang `env =` keyword runs `setenv(ARGS[0], ARGS[1], 1)` in the compositor process (ConfigManager.cpp:1870, handler registered :619), so `env = XKB_CONFIG_ROOT,...` / `env = XKB_DEFAULT_LAYOUT,...` in hyprland.conf DO reach later keymap builds (a keymap built before the env line is parsed would not see it; ordering is [INFERENCE], not traced). Consequence: a layout file at `$XDG_CONFIG_HOME/xkb/symbols/<name>` (or ~/.xkb/symbols/<name>) is found by Hyprland's kb_layout=<name> the same way xkbcli finds it, PROVIDED the compositor process env carries the same XDG_CONFIG_HOME/HOME the test used and the rules file resolves it (rules files are also looked up through the include path: symbols are included, rules are `rules/<name>` in the same path).
5. **Live shape (read-only, 2026-10-26, values withheld).** Compositor process environment: HOME set, XDG_CONFIG_HOME set and equal to $HOME/.config; XKB_DEFAULT_{RULES,MODEL,LAYOUT,VARIANT,OPTIONS}, XKB_CONFIG_ROOT, XKB_CONFIG_EXTRA_PATH all unset. ~/.config/xkb, ~/.xkb, /etc/xkb are absent (consistent with the task's "three user paths could not be added"). No file under ~/.config/hypr mentions XKB_ or XDG_CONFIG_HOME (count 0). So on this host Hyprland's include order is the single root /usr/share/xkeyboard-config-2, identical to the xkbcli receipt.
