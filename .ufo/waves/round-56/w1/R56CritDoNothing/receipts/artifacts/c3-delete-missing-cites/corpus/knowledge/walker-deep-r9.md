## §2 Version/shape deepened

### 2.1 The printed shape (OBS)

`2.17.0\n` — bare semver, no program-name prefix, no build metadata, LF
terminated. Deterministic across repeat runs and locale (`LC_ALL=C`
byte-identical), and identical to its short form `-v`. The option-count
shape: 26 option lines in `--help` = **3 help options** (`--help`,
`--help-all`, `--help-gapplication`) + **23 application options**; there
are **no subcommands** (`Usage: walker [OPTION…]`), unlike the elephant
CLI's subcommand shape. `--help-gapplication` documents the only
service-mode flag, `--gapplication-service`.

### 2.2 The binary shape and build identity (OBS)

From the file bytes, without executing anything:

| Property | Value |
|---|---|
| ELF class/type | ELF 64-bit LSB **pie executable**, x86-64, version 1 (SYSV) |
| linkage | dynamically linked, interpreter `/lib64/ld-linux-x86-64.so.2`, `for GNU/Linux 4.4.0` |
| symbols | **stripped** |
| headers | 12 program headers, 35 section headers, section-name table idx 34, entry point `0x190420` |
| BuildID | `NT_GNU_BUILD_ID` sha1 `a22452d1e4243bad1bf9fd487aa569f673ad9c5a` (also in `file` output) |
| ABI note | `NT_GNU_ABI_TAG` OS Linux, ABI 4.4.0 |
| `.comment` | `GCC: (GNU) 16.1.1 20260430`; `Linker: LLD 22.1.8`; `rustc version 1.97.1 (8bab26f4f 2026-07-14) (Arch Linux rust 1:1.97.1-1)`; `GCC: (GNU) 16.1.1 20260725` |
| package check | `pacman -Qkk walker` → 29 files, **0 altered**; Build Date == binary mtime |

So the artifact identity chain is: printed version → embedded literal
(§2.3) → sha256 → BuildID → package DB (`2.17.0-1`, 0 altered). A future
probe can detect a replaced or rebuilt binary by **any** of the sha256,
BuildID or `.comment` toolchain line moving.

## §3 Config reload semantics

### 3.1 The question and the safety fence

The open question: *what re-reads `config.toml`, when — process start
only, per D-Bus activation, or on file change — and does an edit apply
without a restart?* The assignment's fence: file byte + read-only
`--help` only; if walker is not queryable safely, the unknown stays with
the evidence class named.

Queryability census (from the round-7 help text, unchanged): the only
state-free walker verbs are `--version` and the three `--help*` forms (all
four re-proven state-free here, §6). Everything that could exercise a live
config read is fenced: `-d/--dmenu` starts a session, `-q/--close` and
`-e/--exit` act on the live service, and on D-Bus `Activate`,
`ActivateAction`, `Open` and `CommandLine` all drive the launcher UI
(introspection §3.5). No query verb for configuration exists. Therefore
the live discriminator — edit config, observe without restart — is
**out of remit**, and the residual unknown is recorded with its class
(§3.8, §7).

### 3.2 Evidence A — the help surface is negative (OBS)

`grep -nEi 'config|reload|restart|watch'` over the stdout of `--help`,
`--help-all` and `--help-gapplication` → **0 hits in all three**. There is
no `--config` path override, no `--reload`, no reload-adjacent verb. The
GApplication section adds only `--gapplication-service`. The CLI cannot
reload by construction.

### 3.3 Evidence B — binary token census: no watch machinery, and the
"Reload" tokens are result-list semantics (OBS)

Crate paths in rodata (`config-0.15.19/src/file/source/string.rs`,
`/src/de.rs`, `/src/env.rs`, `/src/source.rs`, `/src/path/mod.rs`) show
config-rs is the loader and confirm the file+env source design
(walker-deep §2.2 stands). A filesystem watcher would have to exist in
this binary; there is no such token, so **there is no hot-reload on file
change** in this build (OBS-negative).

### 3.4 Evidence C — one-shot design signals (OBS/infer)

The two error strings above (`Failed to set loaded config`, `config not
initialized`) describe *setting* an already-loaded config and an
*initialization* state — both one-shot lifecycle words — and sit in
rodata next to the embedded default blob and the `WALKER_`/`config.toml`
path tokens. Combined with the config-crate overlay design (`PartialWalker`
fold, walker-deep §2.2) and the absence of any reload entry point (§3.3),
the read-once model is **INF (high)**; it is not OBS-verifiable without a
live run.

### 3.5 Evidence D — service and D-Bus shape: no reload path (OBS)

- `systemctl --user show app-walker@autostart.service -p CanReload -p
  Restart -p RestartUSec` → `CanReload=no`, `Restart=always`,
  `RestartUSec=2s`; `ExecReload` is unset. systemd cannot reload it either.
- `busctl --user introspect dev.benz.walker /dev/benz/walker` method set:
  `org.freedesktop.Application` (`Activate`, `ActivateAction`, `Open`),
  `org.gtk.Application` (`Activate`, `CommandLine`, `Open`, `Busy`),
  `org.gtk.Actions` (`List`, `Activate`, `Describe`, `DescribeAll`,
  `SetState`, `Set`, `Changed`), plus the standard
  Introspectable/Peer/Properties. **No `Reload`/`ReloadConfiguration`/
  `ReloadConfig` method**; the only state-changing verbs are UI-driving
  and fenced.
- `busctl --user call dev.benz.walker /dev/benz/walker org.gtk.Actions
  List` → `as 0` (empty; re-confirms round 3/7 — there is not even an
  app action that could carry a reload).

### 3.6 Evidence E — the shipped operator path is a restart (OBS)

`~/.local/share/omarchy/bin/omarchy-restart-walker` bytes (read-only):
`systemctl --user restart elephant.service` (when enabled) then
`systemctl --user restart app-walker@autostart.service` (else prints
`Unable to restart Walker -- RESTART MANUALLY`). The user config's only
"restart" mention is the emergency row `Restart Walker` →
`omarchy-restart-walker` (`~/.config/walker/config.toml:47-49`). Neither
config layer's comments documents a reload path. This is the documented
apply path; walker-deep §9's rule ("edit `config.toml`, then `omarchy
restart walker`") therefore stands, now resting on five independent
classes (A–E) rather than on the help negative alone.

### 3.7 The `--help` probe under a broken config — and its limit (OBS)

Recipe: `mkdir -p xdg/{config,data,cache,state,runtime}`; plant
`xdg/config/walker/config.toml` = 26 B of invalid TOML
(`this is = not [valid TOML`); run
`env XDG_CONFIG_HOME=…/xdg/config XDG_DATA_HOME=…/xdg/data
XDG_CACHE_HOME=…/xdg/cache XDG_STATE_HOME=…/xdg/state
XDG_RUNTIME_DIR=…/xdg/runtime walker --help`.

Result: rc 0, stdout **byte-identical** to the baseline `--help`
(`cmp` clean), 0 B stderr, and **no files created** anywhere in the
scratch XDG tree (only the planted file, before and after). Boundary
checks held (§6).

**The limit, stated:** this bounds the *help surface* — `--help` emits no
config-load signal even with a broken config at the XDG config path. It
does **not** by itself distinguish (i) help short-circuits before config
load from (ii) help loads config but a broken user config is tolerated
silently; and it does not independently confirm that this binary honors
`XDG_CONFIG_HOME` (the token census says XDG_* path resolution exists —
round-7 §3 — but honoring was not exercised). Both residual readings stay
UNK (§7.2/§7.3). One usable consequence is OBS: the printed help/version
bytes carry no config signal, so help/version pins are config-independent
as observed.

### 3.8 Verdict — what is settled, what stays, and under which class

**Settled (OBS):** there is no reload verb in the CLI; no reload method on
D-Bus; no systemd reload path (`CanReload=no`, no `ExecReload`); no
filesystem-watch machinery token in the binary; the `Reload`-family
tokens are result-list refresh semantics; the load-time error strings and
config-crate usage describe a one-shot load/set; the shipped operator
path is a service restart; the help output is invariant under a broken
config.

**INF (high):** config is read once at process start; a `config.toml`
edit requires the service to be restarted to take effect. (This is the
walker-deep §9 rule, now on five evidence classes, A–E.)

**UNK (kept, evidence class named):** whether an edited config is picked
up between invocations without a restart — i.e. the *live* half of reload
semantics. It is not queryable safely: every exercise path opens the
launcher (fenced), and process-introspection routes (`/proc`, ptrace) are
barred or unattempted this lane. Round-7 §7's note stands: a stronger
proof is possible if the environment permits ptrace on the *service*
(which would still be a separate, mutation-free observation design, not
this lane's call). The unknown stays with **file-byte + read-only
`--help`** as its named class.
