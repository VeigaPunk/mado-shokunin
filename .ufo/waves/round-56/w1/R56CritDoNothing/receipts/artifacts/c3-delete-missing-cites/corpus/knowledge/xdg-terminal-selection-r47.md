## The chain, step by step

1. Lists and their order. `make_paths` builds two ordered lists and one path. `IFS=':'` (xdg-terminal-exec:145) then the config sequence (xdg-terminal-exec:148-163): for each of `${XDG_CONFIG_HOME:-$HOME/.config}` and `${XDG_CONFIG_DIRS:-/etc/xdg}`, first every lowercased `$XDG_CURRENT_DESKTOP` item as `${dir}/${desktop}-xdg-terminals.list` (xdg-terminal-exec:150-152, the lowercasing done once with `tr` at xdg-terminal-exec:1144), then `${dir}/xdg-terminals.list` (xdg-terminal-exec:153); after both config dirs, the same pair per `${XDG_DATA_DIRS:-/usr/local/share:/usr/share}` inside an `xdg-terminal-exec/` subdir (xdg-terminal-exec:157-163). The result `XTE__CONFIGS` is read left to right as *decreasing* preference, so the two system entries come last - which is what makes an `/execarg_default` line in the distro list (step 2) a low-priority default. The applications list (xdg-terminal-exec:166-169) is built the other way round, each new `${dir}/applications` prepended to the front (`XTE__APPLICATIONS_DIRS=${xte__dir%/}/applications/${XTE__APPLICATIONS_DIRS:+:${XTE__APPLICATIONS_DIRS}}`, xdg-terminal-exec:168), so it ends up in *ascending* preference - lowest-priority data dir first. The cache file is `${XDG_CACHE_HOME:-$HOME/.cache}/xdg-terminal-exec` (xdg-terminal-exec:172-173).
2. List lines. `read_config_paths` reads every list file immediately, in the order of step 1, rather than on demand (`All config files are read immediatelly, rather than on demand, even if it's more IO intensive`, xdg-terminal-exec:353) and pins the locale to `C` by re-invoking itself (xdg-terminal-exec:355-358). A missing file is not an error (xdg-terminal-exec:365). Each line is trimmed by `read -r` and matched by `case`: the five directives `/enable_cache`, `/disable_cache`, `/execarg_compat`, `/execarg_strict` and `/execarg_default:<id>:<arg>` (xdg-terminal-exec:374-421), of which the first two and the first two of the second pair honour only *the first encountered* occurrence via their `*_CONFIGURED` guards (xdg-terminal-exec:376-379); then the entry-ID form `[a-zA-Z0-9_]* | [+-][a-zA-Z0-9_]*)` (xdg-terminal-exec:425). A leading `+` or `-` is cut off as an exclusion marker (xdg-terminal-exec:427-437): `-id` appends to `XTE__EXCLUDED_ENTRY_IDS` (xdg-terminal-exec:462) and `+id` protects an id only from a *later* `-id` (the first of the pair wins; an earlier exclusion stands, fixture `f3-exclude-then-include-still-excluded`), each list refusing duplicates. Only the first `:` splits the line, ID from action ID (xdg-terminal-exec:435-438); both halves must validate (xdg-terminal-exec:439) or the line is discarded with a message (xdg-terminal-exec:467). A plain line is appended to `XTE__ENTRY_IDS` in file order, which is the explicit preference order (xdg-terminal-exec:442). Comments and empty lines match no arm and are ignored.
3. Desktop-file ID lookup. `find_entry_paths` turns IDs into paths with one `find` call (xdg-terminal-exec:754-800). Its argument list starts with `<dir>.` per applications dir (xdg-terminal-exec:762), adds `-type f` (xdg-terminal-exec:766) and, per directory, one parenthesised `-path`/`! -path` pair joined by `-o` (xdg-terminal-exec:773) that admits a file only when its name starts with an alphanumeric character and its path contains no character outside `[a-zA-Z0-9_./-]`, so an ID with any other character is never found at all. `find -L` follows symlinks over the *ascending* order from step 1 (xdg-terminal-exec:795). The `awk` prints each path and then its ID - the part after the last `/./`, with every `/` turned into `-` (`awk '{ print; sub(".*/[.]/", ""); gsub("/", "-"); print }'`, xdg-terminal-exec:797). Each pair is read as two lines and registered as a shell alias named after the ID (xdg-terminal-exec:779, 782); a later registration overwrites an earlier one (xdg-terminal-exec:780), so the *highest*-priority data dir wins the path while the *lowest*-priority found copy is whoever first claimed the ID. The same loop builds `XTE__FALLBACK_ENTRY_IDS` by prepending (xdg-terminal-exec:790), which is why the fallback list ends up in the descending order of step 1; IDs excluded by a `-id` line are skipped first (xdg-terminal-exec:785-788). Nothing here reads a desktop file yet.
4. Validation. Two functions decide whether a registered path is usable. `read_entry_path` (xdg-terminal-exec:970-1018) reads the file line by line with leading/trailing whitespace trimmed (xdg-terminal-exec:985): `[Desktop Entry]` opens the main group and, when no action was requested, allows `Exec` to be read immediately (xdg-terminal-exec:989); a `Key=Value` line matched as `[a-zA-Z0-9-]*` (xdg-terminal-exec:991) is split at the first `=` with the value left-trimmed (xdg-terminal-exec:993-995) and handed to `check_entry_key`; the first key that fails resets the globals and discards the whole entry (xdg-terminal-exec:996-1004). `check_entry_key` (xdg-terminal-exec:802-968), whose own comment marks the order of its tests as significant (xdg-terminal-exec:814), requires `TerminalEmulator` in `Categories` (xdg-terminal-exec:816-828), checks `Actions` membership only when an action was requested (xdg-terminal-exec:829-845), applies `OnlyShowIn`/`NotShowIn` only when the caller says so (xdg-terminal-exec:846-884; the selection loop turns that on for fallback entries only, step 5), expands and stores the `[X-]TerminalArg{Exec,AppId,Title,Dir,Hold}` values (xdg-terminal-exec:885-931), runs `command -v` on `TryExec` (xdg-terminal-exec:933-937), rejects `Hidden=true` (xdg-terminal-exec:938-947), and for `Exec` expands the desktop-entry string escapes (xdg-terminal-exec:501-559), tokenises it with its own shell-word parser that rejects unquoted `` ` $ \ ' > < ~ | & ; * ? # ( ) `` and unclosed quotes (xdg-terminal-exec:561-692), strips the `%` fields - `%f %F %u %U` are removed and only one such field is tolerated, `%i %c` are removed, `%%` becomes `%`, any other field voids the entry (xdg-terminal-exec:694-740) - and then requires the first word on `PATH` (`command -v "$XTE__EXEC0" > /dev/null || return 1`, xdg-terminal-exec:964). An action group `[Desktop Action <id>]` is entered only if `<id>` was listed in `Actions` (xdg-terminal-exec:1005-1012), and any later group header stops the read once `Exec` was seen (xdg-terminal-exec:1014).
5. Selection. `find_entry` walks the explicit list, then a sentinel, then the fallback list, as one newline-separated sequence (xdg-terminal-exec:1060). The sentinel `//fallback_start//` switches `xte__de_checks` on (xdg-terminal-exec:1071-1074), i.e. the show-in tests of step 4 apply to fallback candidates only; an `id:action` candidate is split at its last `:` (xdg-terminal-exec:1062-1068). A missing alias means the ID is not on disk and the candidate is skipped (xdg-terminal-exec:1081); otherwise the alias is evaluated for the path (xdg-terminal-exec:1083), then unaliased so a duplicate ID later in the same list is skipped (xdg-terminal-exec:1085), and `read_entry_path` runs with the current `de_checks` value (xdg-terminal-exec:1086). After a successful read the candidate must still have a non-empty `Exec` (xdg-terminal-exec:1088) and must be a `TerminalEmulator` (`[ -z "${XTE__IS_TERMINAL}" ] && continue`, xdg-terminal-exec:1090); in strict mode an entry without `TerminalArgExec` is skipped, in compat mode (the default, xdg-terminal-exec:1147) it gets `-e` or its `/execarg_default` value from step 2 (xdg-terminal-exec:1092-1100, 1113-1140). The first candidate passing all of it is stored as `XTE__ENTRY_PATH`, `XTE__ENTRY_ID` and `XTE__ENTRY_ACTION` (xdg-terminal-exec:1103-1105); if none does, the resolver prints the applications dirs it searched (xdg-terminal-exec:1109) and exits 1 (xdg-terminal-exec:1208).
6. Exec-arg composition. The option loop (xdg-terminal-exec:1224-1321) consumes leading options: `--` and `-e` (or whatever the entry's exec argument is) end option processing and are dropped (xdg-terminal-exec:1226-1235), `--app-id=`, `--title=` and `--dir=` are split at their `=` (xdg-terminal-exec:1236-1259), `--hold` and `--test` set flags (xdg-terminal-exec:1260-1271), the print flags of step 7 set `XTE__PRINT_DATA`, an unknown `-*` option is discarded (xdg-terminal-exec:1317-1320) and the first non-option ends the parse (xdg-terminal-exec:1313-1316). The command is then assembled by repeated front-prepending (xdg-terminal-exec:1387-1452), one `set -- "$XTE__EXECARG" "$@"` (xdg-terminal-exec:1389) per group, in the order exec argument, hold, dir, title, appid, and finally the entry's own `Exec` words; because every group prepends, the last prepend lands first: [Exec…] [AppId] [Title] [Dir] [Hold] [ExecArg] [command…]. Each key ending in `=` fuses its value into the same argument (xdg-terminal-exec:1403); a key without a trailing `=` yields two arguments (xdg-terminal-exec:1407, 1422, 1437). A requested `--title=`/`--app-id=`/`--hold` that the entry has no key for is dropped silently (xdg-terminal-exec:1396-1398, 1426-1428, 1441-1443), and a requested `--dir=` without `X-TerminalArgDir` is applied with `cd` just before exec instead (xdg-terminal-exec:1494-1497). The exec argument is only prepended when at least one command word follows and the entry's exec argument is non-empty (xdg-terminal-exec:1388) - an empty `TerminalArgExec` therefore produces no argument at all, which is the documented way to say "no exec argument". Everything is then exec'd in the same process (xdg-terminal-exec:1499): the terminal replaces the resolver, it is not forked behind it (README.md:218).
7. Print modes. `XTE__PRINT_DATA` is an unordered set of the words `id`, `path`, `content`, `cmd`, but the output order is fixed: id, then path, then content, then cmd (xdg-terminal-exec:1327-1366, 1468-1490). `--print-id` prints the ID with `:action` appended when an action was selected (`printf '%s' "${XTE__ENTRY_ID}${XTE__ENTRY_ACTION:+:}${XTE__ENTRY_ACTION}"`, xdg-terminal-exec:1331); `--print-path` first removes the `/./` marker the find prefix of step 3 inserted (xdg-terminal-exec:1342) and then prints the path with the same `:action` suffix (xdg-terminal-exec:1349); `--print-content` prints the delimiter first when an item preceded it (xdg-terminal-exec:1358-1360), then the entry's lines (xdg-terminal-exec:1362). The two delimiters are literal printf sequences defaulting to `\n` (xdg-terminal-exec:1222-1223): `--print-delimiter=` between the four data items, `--print-cmd=<seq>` between the words of the command. Both are passed through `printf`'s `%b`, so `\n`, `\t` and similar sequences are interpreted by the shell rather than printed literally. When no `cmd` was requested the run ends there: after content it exits at once, after id/path it adds a newline only when the delimiter is `\n` (xdg-terminal-exec:1368-1385); `--print-cmd` prints one word per delimiter (a newline by default) and adds a trailing newline only when one of the two delimiters is `\n` (xdg-terminal-exec:1486-1490). A `\c` in either delimiter ends the output of that one `printf` call, which the counter's generated cases exercise. Print modes never launch anything: the selected entry is reached, printed and exited.

## The cache, separately

The cache is not part of the selection chain; it is a shortcut in front of it, and it is on by default (`XTE__CACHE_ENABLED=${XTE_CACHE_ENABLED-true}`, xdg-terminal-exec:1172). Unless that variable is falsy the resolver always *tries* to read the file first (xdg-terminal-exec:1179) and, on a hit, skips steps 1-5 entirely - the README states it plainly (`Valid cache bypasses reading of any other file.`, README.md:300-301 - the quote spans two lines of the pin). The key is an md5 (xdg-terminal-exec:179-215) over the literal `4` (the format version, xdg-terminal-exec:194), `$XDG_CURRENT_DESKTOP` and the `ls -LRl` listing of every config and applications path (xdg-terminal-exec:200), so touching any list file, desktop entry or directory in those trees invalidates it. The file holds two-digit-free positional records: ten lines (hash, command, entry path, entry id, action, execarg, appidarg, titlearg, dirarg, holdarg) followed by the command words joined by ASCII Unit Separator and terminated by Record Separator + `END_OF_EXEC_USEP` (xdg-terminal-exec:217-298, the reader; 300-340, the writer). A cache is accepted only when the recomputed hash matches *and* the cached command is still on `PATH` (xdg-terminal-exec:274). Saving happens on a non-cached run that gets past the print bail-out - `--print-cmd`, `--test` or a real launch - forked into the background (`save_cache "$1" &`, xdg-terminal-exec:1455-1458), creating `$XDG_CACHE_HOME` if needed (xdg-terminal-exec:303) and writing with `umask 0077`; a run with only `--print-id`/`--print-path` exits before it (xdg-terminal-exec:1378-1384) and writes nothing. The newline guard at xdg-terminal-exec:312-317 compares the whole concatenation of hash, command and arguments with a lone newline, so it fires only when that concatenation is exactly a newline, not when one argument merely contains one. Two consequences for anyone modelling this: a warm cache hides the list files from the run entirely, and a `--print-cmd` probe refreshes the cache it was meant to observe - both why a tool that must answer "why" models a cold cache, and why every probe of this round pointed `XDG_CACHE_HOME` into scratch.

## What running the script shows that the documents do not

The proposal says every candidate is validated "by the same rules as in Desktop Entry Specification" (xdg-terminal-exec-proposal.md:160-168). The script's validation is narrower and stateful; each item below is a difference the real script prints, with the C1 fixture that shows it.

- Keys carry over between candidates. `reset_keys` runs only when a key check fails (xdg-terminal-exec:996-1002); a candidate read without error but skipped for an empty `Exec` or a missing category (xdg-terminal-exec:1088-1090) leaves `XTE__IS_TERMINAL` and the exec words set, so the next candidate inherits them: a later entry with `Exec` but no `Categories` is selected (fixture `l1-carry-over-category`).
- The read loop's exit status rejects. `read_entry_path` returns the status of the last command its `while` loop ran (xdg-terminal-exec:985-1017); a file whose last processed line is a group header that does not stop the read leaves status 1 and the entry is skipped with no key at fault (fixtures `l1-loop-status-entry-header-last`, `l1-loop-status-other-group-last`).
- `TryExec` is `command -v`, not a file test (xdg-terminal-exec:933-937). The spec asks for an executable file (desktop-entry-spec.xml:636-645); the shell also accepts its builtins (`TryExec=printf`, fixture `l1-tryexec-builtin`), the script's own functions, and the alias of any desktop-file ID registered in step 3 and not yet tried (fixture `l1-tryexec-alias-of-untried-id`; once tried, the alias is gone: `l1-tryexec-alias-already-tried`).
- Lines are what `read -r` returns: leading and trailing blanks dropped, NUL bytes dropped, a carriage return kept, and a last line without a newline never seen (fixture `l1-no-final-newline`: the final `Categories` line is lost and the entry is not a terminal).
- Key tests match the whole line by prefix: `CategoriesX=...` counts as `Categories` (xdg-terminal-exec:816), and only the literal value `true` hides an entry (xdg-terminal-exec:940-941; fixture `l1-hidden-not-exact`); the spec's boolean type allows only `true` or `false` (desktop-entry-spec.xml:298-299), so `True` is out of spec and the script keeps the entry.
- `--title=`, `--dir=` and `--app-id=` values are read with `IFS='=' read`, which drops one trailing `=` from a value that holds no other one (xdg-terminal-exec:1244-1249; fixture `l1-title-trailing-equals`); the same rule applies to the third field of `/execarg_default:<id>:<arg>` (fixture `l1-execarg-default-trailing-colon`).
- A field-code failure keeps the raw words. When `de_strip_fields` meets a second `%f`-class field it returns before writing its result (xdg-terminal-exec:707-710), so the tokenized `Exec` with its `%` words is what `--print-cmd` prints (fixture `l1-strip-fields-failure-keeps-tokens`).
- An unreadable list file ends the run with exit 1 (errexit, xdg-terminal-exec:361-473); an unreadable desktop file only skips that candidate.
- An empty argument (`xdg-terminal-exec --print-id ""`) matches no arm of the option loop and is never shifted (xdg-terminal-exec:1224-1322): the resolver spins forever. A probe harness must never pass one (it cost this round a runaway seat).

## Reading a discard or a DIFFER

- A listed entry that vanishes silently most likely failed step 4: no `TerminalEmulator` in `Categories`, a `Hidden=true`, a `TryExec` not on `PATH`, or an `Exec` whose first word is not on `PATH` - the last two depend on the `PATH` the hotkey's environment carries, not on the entry's text.
- An entry that is found and valid but never selected in strict mode is missing `[X-]TerminalArgExec`; only compat mode supplies `-e` (step 5).
- A `--print-path` pointing at a system file while the user has an override means the override was registered *later* than the system copy, i.e. the ID is not actually present under the user's applications dir, or the user typed a different ID.
- Two runs disagreeing although no file changed usually means the first run wrote a cache the second used (cache section); compare under a fresh `XDG_CACHE_HOME`.
- A `--print-cmd` line that lacks the terminal's `--dir=` argument means the entry has no `X-TerminalArgDir` key: the resolver `cd`s instead (step 6), which is invisible in the printed command.

## Limits

- Launch is not observed: the round answers which entry the resolver selects, not that a terminal process starts from it under the hotkey (`[UNK]`, terminal-route-r17.md:144-145 launch half).

- The desktop-entry specification itself (string escapes, `%` fields, quoting) is modelled here only as far as this script implements it; the script is the judge, not the spec.
- `command -v` semantics are the shell's: builtins, functions and aliases of the running shell would satisfy it, so a sandbox's shell matters to step 4.
- Only the first word of `Exec` is checked for existence; later words are passed through unchecked (computed locator: xdg-terminal-exec:962).
- The fallback order among entries in one directory is the `find` order, which the specification leaves undefined (README.md:179-180); a reimplementation must reproduce libc/GNU `find` order, not invent one.
- What the selected terminal does with the composed arguments (its own `-e`, `--working-directory=`, `--class=` handling) is out of scope; the terminal is never launched in this lane.
- Whether the `--dir=` value from `omarchy-cmd-terminal-cwd` resolves at launch time stays `[UNK]` (terminal-route-r17.md:150-151, helper not run).
- Hyprland's own `exec` path (`uwsm-app --`) is not examined here; only the resolver's side of the hotkey is.
