## The chain, step by step

1. **The handler.** `bind` and its flag variants land in one handler registered as `"bind"` with a required value `m_config->registerHandler(&::handleBind, "bind", {true});`(Hyprland-legacy-ConfigManager.cpp:607); the letters after `bind` are read one by one and an unknown one aborts `default: return "bind: invalid flag";`(Hyprland-legacy-ConfigManager.cpp:1541). The value is split into at most four (five with `d`, plus one with `k`) comma arguments `const auto ARGS     = CVarList(value, numbArgs);`(Hyprland-legacy-ConfigManager.cpp:1555), the key field being `ARGS[1]` - or empty when the `s` flag turns the key into a `&`-separated keysym set `if (multiKey) {`(Hyprland-legacy-ConfigManager.cpp:1567). For every single-key bind the keysym vector stays empty, so the key **string** survives to match time.
2. **`parseKey`.** Four outcomes, in order (Hyprland-legacy-ConfigManager.cpp:1481-1490): a bare number greater than 9 is a keycode `return {.keycode = std::stoi(key)};`(Hyprland-legacy-ConfigManager.cpp:1483), `code:N` is a keycode `else if (key.starts_with("code:") && isNumber(key.substr(5)))`(Hyprland-legacy-ConfigManager.cpp:1484), `catchall` is the catch-all, and everything else is kept verbatim as a name `return {.key = key};`(Hyprland-legacy-ConfigManager.cpp:1489). So `1`..`9` are keysym names while `10` and up are keycodes - a split the wiki does not spell out, and the one this host's digit row depends on.
3. **What is stored.** The parsed key goes into the `SKeybind` aggregate so a bind keeps **both** a key string and a keycode and decides at match time which one it is `SParsedKey parsedKey = parseKey(KEY);`(Hyprland-legacy-ConfigManager.cpp:1617) `g_pKeybindManager->addKeybind(SKeybind{parsedKey.key,`(Hyprland-legacy-ConfigManager.cpp:1624). A bind is only added when the key string is non-empty or the `s` flag is set `if ((!KEY.empty()) || multiKey) {`(Hyprland-legacy-ConfigManager.cpp:1616), so `bind = SUPER, , exec, x` registers nothing; the catch-all is refused outside a submap `Catchall not allowed outside of submap!`(Hyprland-legacy-ConfigManager.cpp:1620).
4. **The key name is resolved at match time, twice.** The keysym branch asks for the exact spelling `const auto KBKEY      = xkb_keysym_from_name(k->key.c_str(), XKB_KEYSYM_NO_FLAGS);`(Hyprland-KeybindManager.cpp:710) and then for a case-insensitive one `const auto KBKEYLOWER = xkb_keysym_from_name(k->key.c_str(), XKB_KEYSYM_CASE_INSENSITIVE);`(Hyprland-KeybindManager.cpp:711), accepting the pressed keysym if it equals either `if (key.keysym != KBKEY && key.keysym != KBKEYLOWER)`(Hyprland-KeybindManager.cpp:724). A bind whose name resolves to nothing is skipped `if (KBKEY == XKB_KEY_NoSymbol && KBKEYLOWER == XKB_KEY_NoSymbol) {`(Hyprland-KeybindManager.cpp:713) - so a misspelt keysym name is a bind that silently never fires. The name the user writes is documented as the header name without its prefix `for all the keysyms. The name you should use is the segment after`(wiki-Binds.md:40).
5. **What `from_name` accepts.** With no flags only the exact spelling resolves, through a perfect hash `size_t pos = keysym_name_perfect_hash(name);`(xkbcommon-keysym.c:252) over generated tables `This file comes from libxkbcommon and was generated by update-keysyms-names-handling.py`(xkbcommon-ks_tables.h:3). With the case-insensitive flag a sorted search runs and, on duplicates, keeps the lower-case name `The "best" case-insensitive match is the lower-case keysym name.`(xkbcommon-keysym.c:268) - which is why step 4's second call makes `Delete`, `DELETE` and `delete` resolve alike. Two notations are parsed after the table lookup fails, without normalization `if (*name == 'U' || (icase && *name == 'u')) {`(xkbcommon-keysym.c:305) `else if (name[0] == '0' && (name[1] == 'x' || (icase && name[1] == 'X'))) {`(xkbcommon-keysym.c:325), then the `XF86_`-without-underscore fallback `if (strncmp(name, "XF86_", 5) == 0 ||`(xkbcommon-keysym.c:338); everything else is `XKB_KEY_NoSymbol`.
6. **Which keysym of the pressed key enters the comparison.** `onKeyEvent` adds 8 to the libinput keycode `const auto         KEYCODE = e.keycode + 8;`(Hyprland-KeybindManager.cpp:367) and reads one symbol from one of two states `pKeyboard->m_resolveBindsBySym ? pKeyboard->m_xkbSymState : m_xkbTranslationState`(Hyprland-KeybindManager.cpp:369). A second read on the fully-updated per-keyboard state `const xkb_keysym_t internalKeysym = xkb_state_key_get_one_sym(pKeyboard->m_xkbState, KEYCODE);`(Hyprland-KeybindManager.cpp:370) is used only for Escape/DnD and for the internal binds it feeds `handleInternalKeybinds(internalKeysym)`(Hyprland-KeybindManager.cpp:377) `bool CKeybindManager::handleInternalKeybinds(xkb_keysym_t keysym) {`(Hyprland-KeybindManager.cpp:928-942). The bind matcher never sees the modifier-translated symbol.
7. **The two candidate states.** `m_xkbTranslationState` is a single global state the keybind manager builds from `input:kb_file` or the `input:kb_*` names in its own context `const auto        PCONTEXT   = xkb_context_new(XKB_CONTEXT_NO_FLAGS);`(Hyprland-KeybindManager.cpp:311) `m_xkbTranslationState = xkb_state_new(PKEYMAP);`(Hyprland-KeybindManager.cpp:332); its only other references are the unref `m_xkbTranslationState = nullptr;`(Hyprland-KeybindManager.cpp:293), a rebuild after config reload, and the read at Hyprland-KeybindManager.cpp:369 - it is **never** given a modifier or group update, so it stays on group 0 of the configured names. `m_xkbSymState` is the per-keyboard state, created from that keyboard's own keymap in the early-return branch the single call site always takes `updateXKBTranslationState(m_xkbKeymap);`(Hyprland-IKeyboard.cpp:118) `if (keymap) {`(Hyprland-IKeyboard.cpp:214), and every update it receives passes zeros for depressed, latched and locked and only the group `xkb_state_update_mask(m_xkbSymState, 0, 0, 0, 0, 0, group);`(Hyprland-IKeyboard.cpp:382) `xkb_state_update_mask(m_xkbSymState, 0, 0, 0, 0, 0, m_modifiersState.group);`(Hyprland-IKeyboard.cpp:422). Because of that branch the layout-splitting loop at Hyprland-IKeyboard.cpp:221-271 is unreachable from the call site read here.
8. **Which level that state resolves.** `get_one_sym` starts from the layout of the state's group `const xkb_layout_index_t layout = xkb_state_key_get_layout(state, kc);`(xkbcommon-state.c:1345), then asks the key type for a level `/* If we don't find an explicit match the default is 0. */`(xkbcommon-state.c:112). The type entry is chosen by exact mask equality `type->entries[i].mods.mask == mods`(xkbcommon-state.c:91), and with no modifiers the base entry matches `return (entry) ? entry->level : 0;`(xkbcommon-state.c:116). Both states therefore resolve the level-1 symbol of the group - no Shift, no Ctrl, no Caps. Modifiers cannot change *which* symbol is compared; they can only change whether the mask matches (step 12).
9. **`input:resolve_binds_by_sym` picks the group.** The option is a per-device integer read at keyboard setup `getDeviceInt(devname, "resolve_binds_by_sym", "input:resolve_binds_by_sym")`(Hyprland-InputManager.cpp:1224) and stored on the keyboard `pKeyboard->m_resolveBindsBySym = RESOLVEBINDSBYSYM;`(Hyprland-InputManager.cpp:1241), default `false` `MS<Bool>("input:resolve_binds_by_sym", "Determines how keybinds act when multiple layouts are used.", false,`(Hyprland-ConfigValues.cpp:278). The wiki states both readings `If false, keybinds will always act as if the first specified layout is active.`(wiki-Variables.md:219) and repeats the rule in the layout section `The first layout defined in the input section will be the one used for binds by`(wiki-Binds.md:462) `In that case, binds will activate when the symbol`(wiki-Binds.md:469). With `0` the group is the one `m_xkbTranslationState` was built with - group 0, the first configured layout, for the life of the state, even after the user switches layout. With `1` the group tracks the pressed keyboard's active layout, still at level 1.
10. **The mask is parsed from a string by substring.** `stringToModMask` uppercases the field and tests `contains` for each name `if (mods.contains("SHIFT"))`(Hyprland-KeybindManager.cpp:224) and `if (mods.contains("SUPER") || mods.contains("WIN") || mods.contains("LOGO") || mods.contains("MOD4") || mods.contains("META"))`(Hyprland-KeybindManager.cpp:236), with `CAPS`, `CTRL`/`CONTROL`, `ALT`/`MOD1`, `MOD2`, `MOD3` and `MOD5` in between. It is a substring test, not a token test: `SUPER SHIFT`, `SHIFTSUPER` and `SUPERSHIFT` set the same two bits. A non-empty field that sets no bit is a config error `Invalid mod, requested mod`(Hyprland-legacy-ConfigManager.cpp:1603).
11. **The bits are one per core modifier.** `HL_MODIFIER_SHIFT = (1 << 0),`(Hyprland-IKeyboard.hpp:13-22) through `HL_MODIFIER_MOD5  = (1 << 7),`(Hyprland-IKeyboard.hpp:21) sit in libxkbcommon's real modifier order, so a bind's mask and the comparison mask use the same bit positions by construction. The runtime side maps the keymap's own indices onto that same order through the mod-name list `constexpr static std::array<const char*, 8> MODNAMES = {`(Hyprland-IKeyboard.cpp:18) `m_modIndexes[i] = xkb_map_mod_get_index(m_xkbKeymap, MODNAMES[i]);`(Hyprland-IKeyboard.cpp:139), OR-ing `1 << i` over the depressed and latched masks `uint32_t modMask = m_modifiersState.depressed | m_modifiersState.latched;`(Hyprland-IKeyboard.cpp:360). What the bind comparison is fed is `m_lastMods`, the depressed mask of the event merged across keyboards that share state `m_lastMods         = MODS.depressed;`(Hyprland-InputManager.cpp:1711) `uint32_t CInputManager::getModsFromAllKBs() {`(Hyprland-InputManager.cpp:1887-1889). Caps Lock and Num Lock are *locked* mods, so they never enter it even though `CAPS` and `MOD2` parse: `bind = CAPS, ...` parses, appears in the dump, and can never fire.
12. **The mask comparison is exact equality, with one escape hatch.** The gate compares the masks directly `modmask != k->modmask && !k->ignoreMods`(Hyprland-KeybindManager.cpp:652), relaxed only by the `i` flag `Will ignore modifiers.`(wiki-Binds.md:82), the submap equality and the shadow flag. Nothing masks Caps or NumLock at compare time; they were excluded at build time.
13. **The per-key branch order.** After the mask gate the branches run in this order: multi-key sets, then the `s`-flag set `} else if (!k->sMkKeys.empty() && key.keyName.empty()) {`(Hyprland-KeybindManager.cpp:671), then the string path for mouse, switch and wheel events `if (key.keyName != k->key)`(Hyprland-KeybindManager.cpp:694), then the keycode path `if (key.keycode != k->keycode)`(Hyprland-KeybindManager.cpp:697), then catch-all `} else if (k->catchAll) {`(Hyprland-KeybindManager.cpp:699), and finally the keysym path at Hyprland-KeybindManager.cpp:702-726. A `code:` bind has an empty key string and so reaches the keycode branch; a name bind reaches the keysym branch. `keyName` is only set by the non-keyboard paths, so a keyboard event never takes the string-equality branch.
14. **Keycode numbering.** The event keycode is `e.keycode + 8` (step 6) and the bind's number is used as-is (Hyprland-legacy-ConfigManager.cpp:1483-1489), so `code:N` and a bare `N > 9` are XKB keycodes, evdev + 8. The wiki says the same in user terms `If you want to bind by a keycode, you can put it in the KEY position with`(wiki-Binds.md:42) `This will bind <key>SUPER</key> + <key>t</key> since <key>t</key> is keycode 28.`(wiki-Binds.md:49). An off-by-8 keycode is a bind that never fires and reports nothing.
15. **The non-keyboard key forms.** Mouse buttons arrive as a synthetic key name `const auto KEY_NAME = "mouse:" + std::to_string(e.button);`(Hyprland-KeybindManager.cpp:488), documented as `hl.bind("SUPER + mouse:272", hl.dsp.exec_cmd("amongus"))`(wiki-Binds.md:111). Wheels arrive as `mouse_down` `{.keyName = "mouse_down"`(Hyprland-KeybindManager.cpp:461) and `mouse_up`, horizontally as `mouse_left`/`mouse_right`; switches arrive as prefixed names `{.keyName = "switch:" + switchName`(Hyprland-KeybindManager.cpp:537), documented as `hl.bind("switch:on:[switch name]"`(wiki-Binds.md:144). All of them travel the string branch (step 13), i.e. by equality with the key field, and none can be reached by a keysym name.
16. **Two binds on one key: config order plus shadowing.** Binds are appended in parse order `m_keybinds.emplace_back(KEYBIND);`(Hyprland-KeybindManager.cpp:189) and scanned in that order `for (auto& k : m_keybinds) {`(Hyprland-KeybindManager.cpp:634); the wiki records the user-visible rule `### Multiple binds to one key`(wiki-Binds.md:155). After a press that suppresses the event `void CKeybindManager::shadowKeybinds(const xkb_keysym_t& doesntHave, const uint32_t doesntHaveCode) {`(Hyprland-KeybindManager.cpp:855) runs, marking every bind whose name resolves to the pressed keysym or its upper form `const auto KBKEYUPPER = xkb_keysym_to_upper(KBKEY);`(Hyprland-KeybindManager.cpp:874) or whose keycode matches, except the one that fired. `global` handlers and `transparent` binds opt out `if (k->handler == "global" || k->transparent)`(Hyprland-KeybindManager.cpp:867) `Cannot be shadowed by other binds.`(wiki-Binds.md:81). So a keysym bind and a `code:` bind on the same physical key do not both fire once either consumes the press; before that, the first in config order wins.
17. **Several matches at once.** Every bind that passes the gates is collected and dispatched after the loop `bindsHit.emplace_back(k);`(Hyprland-KeybindManager.cpp:773), so `ALT, TAB` = `cyclenext` + `bringactivetotop` runs both, in order. `release`, `nonConsuming` and `autoConsuming` decide only whether the event is swallowed `if (pressed && k->release && !SPECIALDISPATCHER) {`(Hyprland-KeybindManager.cpp:728) `} else if (!k->release && !SPECIALDISPATCHER) {`(Hyprland-KeybindManager.cpp:747), not whether the neighbour runs. On release the gate is re-tested against the mask recorded at press time `if (key.modmaskAtPressTime != modmask && !k->ignoreMods) {`(Hyprland-KeybindManager.cpp:738), so letting a modifier go between press and release does not change which bind fires.
