## B. Reusable rules/fixtures for mado

1. **Keep-ref rule for landedness (souji).** `refs/jj/keep/*` are GC grace refs, never receipts; durable-root enumeration is `for-each-ref --exclude='refs/jj/'`, and a keep-only commit counts as unpushed work only when it introduces a novel blob at the target (`souji-verify.sh:61-77,241-250`; zero-cost when no keep refs exist). mado's round-19 `landed-check.sh` should reuse this spelling verbatim rather than derive its own; mado's drafted `vcs_write` class needs no change (it classifies commands, not repo state).
2. **jj-red-before sandbox (kaidoku) is the proven red/green harness** if mado ever needs to *demonstrate* jj behavior (e.g. that a snapshot-read really writes): origin removed + fake remote ref, `GIT_*/JJ_*/TMPDIR` stripped, sandboxed HOME/XDG, `-R`, mkdtemp refused under lane/fleet roots (`jj-red-before.py:1-14,113-123,224-287`). mado's r19 `r19-vcs` fixtures are synthetic JSONL and need none of it — keep them hermetic; cite kaidoku's harness only if a behavior probe is ever demanded.
3. **Branch-tip pinning has four sibling spellings; pick one for mado's F6 fix**: tsukuroi (reject all non-hex, ancestry vs `refs/heads/<branch>`), tabi (attached→own branch, detached→refs/heads ladder, anchor must be one direct ref), tameshi (`detect_branch` mirror of the fleet helper, `head_differs_from_branch` recorded, never fatal), kaidoku (pin `refs/heads/main`, refuse `head_not_branch_tip`; note their w2 finding that `@`, `HEAD~0`, `HEAD^{commit}` escape a literal-`HEAD` refusal — `w2/GatePINMAP.md` decision-table limit row). mado's carried F6 (HEAD detaches) fix should name which of these it follows; tabi's detached-HEAD-at-poison-commit fixture (`check-round-contract.mjs:807-811`, `selftest-measurement-binding.mjs:439-455`) is the cheapest red-before shape.
4. **Environment guard for git-shelling fixtures (tameshi).** Any mado fixture that runs `git` (frozen replay pinning, landed-check selftests) must scrub `GIT_DIR/GIT_WORK_TREE/GIT_INDEX_FILE` first — tameshi recorded a real incident where a caller-exported `GIT_DIR` committed fixture writes into the live repo (`mutate-and-run.sh:249-253`). Extend the scrub to `JJ_*` (kaidoku does: `jj-red-before.py:113-117`).
5. **Record-and-refuse canary pattern (mori).** Canary binary on PATH → append argv to a log → non-empty log is a named fail reason (`path_journalctl_tripwire` / `bare_journalctl_tripwire`). Directly transferable if mado ever builds a hermetic harness that must prove "no live walker/waybar/hyprland binary was reached" under the host pause.
6. **Source-audit ban regex (souji) as the model for stated limits.** mado's `TwVcsClass.r19.patch` docstring already lists what is *outside* `vcs_write` (`git fetch, revert, tag, branch, clean, worktree, gc, config`; aliases/functions/scripts) — souji's history shows such lists get attacked by scouts and then patched (r16 F2 found the `--alternate-refs` consumer gap at the then-`:1729`; current bytes `:2010` include it). Keep the outside-list adjacent to the `r19-vcs` suite and expect it to grow by the same route.

## C. Conflicts / contradictions with mado's planned classes

1. **Vocabulary conflict (already flagged inside mado; scan confirms it is fleet-internal only):** round-18 draft token `tool_install` (`TwInstallerChannels.patch`: `CLASSES = (…, "tool_install")`) vs round-19 spec/dispatch name `installer` (`.ufo/waves/round-19/gen_w1.py:57`, and `.ufo/waves/round-19/drafts/SkillRegistryDraft.md:42-46,78-79` marks it "open L1 decision"). No sibling uses either token, so L1 can pick freely; recommend `tool_install` (it is what the applied-against patch bytes say, and "installer" collides with the Omarchy-installer sense that dominates sibling text).
2. **Classification ≠ authorization (normative tension to word carefully).** mado's r19 spec says the installer class exists because "the operator AUTHORIZES installs via uv tool/npx/official binaries (RULES.md), so the class must be permit-able and must not be host_mutation" (`gen_w1.py:57`). kaidoku's round-14 probe hit the same RULES-vs-PROVINCE seam and resolved it as: RULES authorizes, the lane's PROVINCE can still forbid, and the tension is recorded as an L0 question rather than settled in-lane (`.ufo/waves/round-14/w1/CustodySafety.md:35-37,86-87`). mado's SKILL note for the new class should state that a `--permit tool_install` verdict records what was issued, never that the lane may install — otherwise the round-18 lesson pattern (rubric gaming via permissive permits) applies.
3. **Scope overlap with souji is real but disjoint.** souji's census source-audit bans git-write subcommands in *its own tool's bytes* (`souji-census.sh:2008-2013`); mado's `vcs_write` classifies *transcript-issued* commands. Different objects, no shared fixture, no claim collision: souji's own overlap table assigns repo-hygiene census to souji (`round-16/w1/SiblingOverlap.md:15-18`), and tameshi's r17 table had already assigned "post-hoc no-harm monitor over OMP JSONL" to mado (`.ufo/waves/round-17/w1/C01SiblingOverlap.md:53`). One substantive delta worth recording: souji's ban list (`fetch|push|commit|branch|checkout|reset|rebase|prune` + `--alternate-refs`) and mado's `GIT_WRITE` (`add, commit, stash, checkout, switch, reset, pull, push, restore, rebase, merge, cherry-pick`) disagree in both directions — souji bans `fetch`/`prune`/`branch`, mado's draft explicitly leaves `fetch` out and never mentions `am`/`apply`/`filter-branch`/`worktree`(write arms). Neither list is wrong (different threat models), but L1 should not treat them as the same class under two names.
4. **Stale draft note (contradiction inside mado's own round-19 tree).** `drafts/SkillRegistryDraft.md:43-45` states `vcs_write` "has no draft class token in `.ufo/waves/round-18` or `.ufo/waves/round-19`", while `drafts/TwVcsClass.r19.patch` exists in the same tree with the full `vcs_write` implementation (docstring, `classify_jj`/`classify_git`, `CLASSES` line) — the note was written before (or without seeing) the patch. L1 must re-read the drafts dir at integration time; divergent SKILL text wins per that draft's own note (`:37`).
5. **`jj` snapshot-read rule vs sibling lane practice — consistent, but stricter than every sibling.** mado's class flags `jj log|status|diff` without an exact pre-`--` `--ignore-working-copy` as `vcs_write` (patch docstring + fixture `jj-snapshot-reads.jsonl`), matching mado's own round-14 lesson that a read-only `jj log` created local snapshot state (via tameshi `.ufo/waves/round-17/w1/C01SiblingOverlap.md:55`). kaidoku's contract instead bans `jj` in-lane entirely (`contract.md:20`) — under mado's class those lane rules would never fire (no command issued), and under kaidoku's rule mado's `--ignore-working-copy` carve-out is unreachable nicety. No action needed; the two policies are compatible layers, but the mado SKILL row should say the class enforces the *fleet* transcript rule, not any lane's stricter ban.
6. **Helper exemption matches the fleet helper's actual write window.** `jj-lane.sh commit` internally runs `jj commit` → `bookmark set` → push (`jj-lane.sh:230-234`, via kaidoku `.ufo/waves/round-18/w1/RevBaseCitationRev.md:106-108`), and mado exempts the helper invocation, not bare `jj commit` — correct: the exempted string is the sanctioned fleet path, and anything typed as raw `jj …` stays a finding. No sibling treats bare `jj` writes as safe, so no conflict.
