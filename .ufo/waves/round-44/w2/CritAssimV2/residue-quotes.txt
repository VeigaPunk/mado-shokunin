== r9 §2 fetchClass quote lines ==
26: ### §2 The link that was missing: class *is* the Wayland app_id
27: 
28: **OBS** Hyprland's own `fetchClass()` defines what a window's class is for a
29: native Wayland surface (S284):
30: 
31: > "return m_xdgSurface->m_toplevel->m_state.appid;"
32: 
33: **OBS** gkeep declares that app_id itself (S285):
34: 
35: > "application_id=\"org.omarchy.gkeep\","
36: 
37: **OBS** The host's rule file matches on exactly that string (S292):
38: 
39: > "windowrule = size 420 500, match:class ^(org.omarchy.gkeep)$"
40: 
41: **INF** The chain is therefore closed at every link that can be checked
42: without a running window. The rule's `match:class` is tested against the
43: Wayland `app_id`, not against an X11 `WM_CLASS` and not against a title;
44: gkeep's app_id is the string the rule's regex matches; and because the rule
45: also floats the window, the `size` effect applies — upstream's own description
46: of that effect is that it "Resizes a floating window." (S287).

66: ### §4 An annotation on where this link is documented — and where it is not
67: 
68: **OBS** The window-rules page, which documents the `size` effect and every
69: match property, never mentions `app_id` (0 occurrences in the page). So the
70: derivation that Hyprland's `class` *is* the Wayland `app_id` for a native
71: surface is stated in exactly one place — the compositor's own source (S284) —
72: and in no piece of upstream documentation.
73: 
74: **INF** That is worth recording as a limitation of the whole chain. The rule
75: key's provenance is undocumented, which is why four rounds treated `class` as
76: an opaque label and why the match could not be decided from the wiki alone.
