Probe design: the probe is a COMPILED C PROGRAM (probe.c), not a shell script,
because a shell script's $0 is the script path as exec'd, not the argv[0] the
program received.  Each spawn writes ONE record into its own file, named with a
sequence number assigned under an exclusive fcntl lock (round-98 lessons
M98-1/M98-7: a shared output file races and a multi-spawn launch then looks
like "the last argument wins").  The terminal stand-in is a second compiled C
program that records the vector it was handed and then execvp's the program, so
the PROGRAM's own argv0/cwd are observed under a terminal.
Cross-check: 54 cases x 2 passes in the v6 set -> agree=54 disagree=0; the v8,
v9, v10, v11 sets were re-run the same way and agreed.

The three measured facts that decide the C1 model:

  (a) UNDER A TERMINAL THE PROGRAM TOKEN IS NOT ABSOLUTISED.
      v8_token_relative_kgx   (Exec=probe, Terminal=true, probe on the PATH):
        the terminal receives  TERM_ARGV0={root}/bin/kgx
                              TERM_ARGC=2  TERM_A0=-e  TERM_A1=probe
        the program receives  ARGV0=probe      <-- RAW, not {root}/bin/probe
      v8_token_absolute_kgx   (Exec={root}/bin/probe):
        TERM_A1={root}/bin/probe ; the program receives ARGV0={root}/bin/probe
      Contrast, no terminal (v6 base_ok): the program receives
        ARGV0={root}/bin/probe  <-- ABSOLUTE.
      => The candidate must NOT absolutise argv[0] when Terminal=true.  The
         vector handed to the terminal is [terminal_abs, exec_arg?, token, ...]
         with the token RAW; the terminal resolves it itself.

  (b) THE PREPEND COMES FIRST, SO THE TERMINAL WINS THE TABLE ORDER EVEN WHEN
      IT IS ONLY IN THE WORKING DIR, BUT THE WORKING DIR DOES NOT OVERRIDE THE
      TABLE ORDER.
      v9_wd_kgx_vs_path_xdg  (kgx=row 1 in Path=, xdg-terminal-exec=row 0 on PATH)
        -> the terminal is {root}/bin/xdg-terminal-exec  (row 0 wins)
      v9_wd_kgx_vs_path_xterm (kgx=row 1 in Path=, xterm=row 11 on PATH)
        -> the terminal is {root}/wd/kgx                (row 1 beats row 11)
      v9_wd_xdg_vs_path_kgx  (xdg-terminal-exec=row 0 in Path=, kgx=row 1 on PATH)
        -> the terminal is {root}/wd/xdg-terminal-exec
      => the per-row search order is: table order first, and WITHIN one row the
         working dir is tried before the PATH walk (gutils.c G10 + G1).

  (c) THE PROGRAM LOOKUP PREFERS THE WORKING DIR OVER THE PATH.
      v10_load_gate_working_dir_wins (probe in both {root}/wd and {root}/bin):
        ARGV0={root}/wd/probe     <-- the working dir wins
      v10_load_gate_path_only     (probe only in {root}/bin):
        the load gate PASSES (the program is found on the PATH) and the launch
        then fails on the cwd: "Failed to change to directory "{root}/wd"".
      v9_working_dir_only         (probe only in {root}/wd, PATH has no probe):
        ARGV0={root}/wd/probe     <-- the load gate finds it in the working dir
      => g_find_program_for_path(program, PATH, Path=) resolves the program
         against Path= FIRST (G1 makes the program absolute), and only falls
         back to the PATH walk when that misses.

5. SHAPES I COULD NOT MAKE gio ANSWER  (command + observed output)
================================================================================
Nothing in the eight named shapes failed.  These are the shapes the surface
cannot reach, each with the command and the observed output:

  (i) A RELATIVE PATH ENTRY RESOLVED *WITHOUT* a working dir, where the entry
       does not exist under the launcher cwd.  Command:
         env -i LC_ALL=C HOME=<root>/h PROBE_OUT=<root>/out/rec PATH=nosuchrel \
           /usr/bin/gio launch <root>/app.desktop
       Observed: gio: Unable to load application information for
       '<root>/app.desktop'  (rc=1).  The shape is unreachable as a LAUNCH:
       gutils.c:486-487 tests the candidate relative to the process cwd, so a
       relative PATH entry can only ever hit under the launcher cwd.  The
       relative-entry shape is therefore only meaningful WITH a working dir.

  (ii) AN ABSOLUTE Exec THAT IS A DIRECTORY, WHERE THE DIRECTORY IS ALSO
       REACHABLE AS A RELATIVE PATH ENTRY.  Command:
         env -i ... PATH=<root>/relbin /usr/bin/gio launch <root>/app.desktop
       with Exec=adir and <root>/relbin/adir a directory.  Observed: the load
       refusal ("Unable to load application information").  I could not separate
       "the directory was rejected" from "the program was not found" in the
       relative-PATH-entry form: BOTH produce the identical refusal text, so
       this shape carries no signal.  The signal is only in the absolute form
       (v6 exec_is_directory_abs), where the :359-365 arm returns NULL on its
       own.

  (iii) THE ORDER OF THE R3 LOOKUP RELATIVE TO THE PREPEND, ISOLATED.  A case
       that would show it needs argv[0] to change identity between the two
       blocks, which GIO does not do: the prepend at :3027 replaces argv[0]
       with the terminal, and the R3 test at :3066 then sees the terminal.  I
       could not build a case where BOTH the prepend and a lookup of the
       PROGRAM token happen; the source order settles it, and the measurement
       in (a) above is the observable consequence.

  (iv) A TERMINAL THAT RESOLVES THE PROGRAM TOKEN ITSELF.  Every real
       terminal would, but the stand-in has to be told where the program is;
       the vector GIO hands the terminal is fully measured (the TERM_ARGV*
       records), and the PROGRAM's own argv0 under a terminal is therefore a
       property of the terminal, not of GIO.  The C1 model must answer the
       vector, not the terminal's re-exec.

  (v) THE SPAWN ORDER OF A MULTI-SPAWN LAUNCH *UNDER A TERMINAL*.  Measured:
       the two spawns are sequential and in argument order (v6
       pctf_two_args_terminal: seq 1 = f1.txt, seq 2 = f2.txt), but the
       ORDINAL of concurrent spawns is not observable here because the two
       children are sequential by construction.  The r98 limit carries.

  (vi) GIO_LAUNCHED_DESKTOP_FILE WHEN THE DESKTOP FILE IS LOADED BY ID
       (g_desktop_app_info_new_from_desktop_id) rather than by filename.  The
       `gio launch` CLI only takes a path (gio-tool-launch.c:91), so this
       shape is not reachable from the CLI at all.

  (vii) THE PORTAL / DBusActivatable PATH.  Not reachable from `gio launch`
       with a plain desktop file and no session bus; the r98 limit carries.

  (viii) A Path= THAT IS AN ABSOLUTE SYMLINK TO A DIRECTORY.  Not measured:
       chdir() resolves it and the child reports the RESOLVED path, but I did
       not build the fixture, so I make no claim about it.

  (ix) THE "cwd-failed" CAUSE WHEN PATH= IS RELATIVE AND EXISTS RELATIVE TO A
       DIFFERENT cwd.  Measured only in the two forms above (relative Path=
       that does not exist under the launcher cwd -> "No such file or
       directory"; Path= naming a regular file -> "Not a directory").  The
       errno text for a relative Path= that exists but is not searchable was
       not exercised.

  (x)  THE EXACT BYTES OF A TERMINAL'S OWN ARGV0 WHEN THE TERMINAL IS
       FOUND *ONLY* THROUGH A RELATIVE PATH ENTRY JOINED WITH Path=:
       measured as {root}/wd/relbin/kgx (v8_terminal_via_relative_entry).

6. WHAT THIS MEANS FOR THE C1 CANDIDATE (the five rules, as they must be coded)
================================================================================
  R1  the load gate: TryExec first (:1947-1959), then Exec's argv[0] (:1974-2006);
      both through g_find_program_for_path(token, NULL, Path=); a miss is a LOAD
      refusal ("Unable to load application information for '<desktop>'"), rc 1.
  R2  the terminal: the twelve rows in table order; per row the working dir is
      tried BEFORE the PATH walk; first hit wins; the vector becomes
      [terminal_abs_path, exec_arg?, <the ORIGINAL argv...>] and the exec_arg is
      present for every row except xdg-terminal-exec.
  R3  the argv[0] lookup at :3066-3101 RUNS ONLY WHEN THERE IS NO TERMINAL.
      With a terminal, argv[0] is the terminal and the program token is passed
      through RAW.  Without a terminal, a relative token is replaced by the
      absolute path g_find_program_for_path returns, and a miss is
      "Program '%s' not found in $PATH".
  R4  the cwd: the child's cwd is Path=, and an empty Path= is normalised to
      NULL (:2062-2066) so it inherits the launcher's cwd.  A Path= that cannot
      be entered is a spawn failure ("Failed to change to directory ...").
  R5  the env: GIO_LAUNCHED_DESKTOP_FILE = the canonicalised desktop path.
  R6  the lookup semantics: the working-dir join first (G1), the absolute
      branch without a PATH walk (G2), the executable-and-not-a-directory test
      (G3/G11), the PATH default when PATH is unset (G8), an empty PATH entry
      meaning the current directory (G9), a relative PATH candidate joined with
      the working dir (G10), a relative hit absolutised against the process cwd
      (G12).

The single most likely mutant to survive a naive implementation: absolutising
the program token under a terminal (measured to be wrong: ARGV0=probe, not the
absolute path).  The second: resolving the program against the PATH before the
working dir (measured: the working dir wins).
