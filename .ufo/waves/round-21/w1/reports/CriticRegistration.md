# CriticRegistration — M13 order and independent-oracle attack

## Axes

- **C2 calibration / process independence:** the artifact-only gate can authenticate the current bytes and still accept a post-hoc “pre-registration.” This is the primary defect: the design does not yet establish chronology of *actual measurement events*.
- **C1 operability / no-harm evidence:** truth-fixture results are only prospective evidence if their expectations were frozen before the implementation/draft outcome was known. Otherwise they are targeted confirmation, not independent acceptance evidence.

## Strongest local counterexample: round-20 M13

This is an observed process failure, not a hypothetical: `corpus/lessons/round-20.md:27` says attempt-2 registration `6a7d9ca` was written **after a sandbox draft had been measured**. The attempt-2 populations predated that draft and nine fixtures were written first; those facts did not make the registration prospective. The source marks the capture authority as “L1 self-report.” `corpus/lessons/round-20-verifier-spotcheck.md:81` independently routes the repair as committing registration and before-receipts before tool results are examined. The focused review records the consequence: the A2 red-to-green guard is targeted confirmation, not blind prospective evidence (`.ufo/waves/round-20/a2/review/CriticAdmission.md:44-51`).

That counterexample defeats a gate that only checks present fixture hashes, says oracle files were committed before gate implementation, or compares registration and implementation commit ancestry. A draft can be measured in an untracked sandbox first; later the author commits the registration, freezes expectations consistent with the observed result, and commits the production implementation afterward. The final tree can have immutable, correctly hashed fixtures and an apparently ordered commit graph while retaining the exact M13 leak. **[INFERENCE]** Any proposed gate limited to those artifact checks would accept this sequence unless it requires a durable receipt for the earlier measurement event and binds it to the measured draft bytes.

## Specific failure modes in the current design

1. **Uncommitted / alternate-copy measurement escapes ancestry checks.** Git ancestry orders commits, not execution events on `/tmp`, an untracked worktree, or a copied draft. M13 is direct evidence that a later registration can coexist with older fixture populations. Require the measurement receipt to bind the actual source snapshot digest, including untracked files, not just a later `HEAD`.
2. **Retrospective receipt and timestamp laundering.** The clarification correctly says timestamps are artifact assertions unless bound to provenance (`registration.md:21`), but Git commit ancestry only orders the commits in that graph; it does not prove when a sandbox run happened. Author/committer dates are editable, clocks may differ, and a receipt written after a run can assert an earlier time. A hash authenticates bytes, not the time or event that produced them.
3. **“Independently authored” is only a label without a sealed authoring trail.** A fixture may be authored after a pilot result, then committed before the gate implementation. A provenance field or explanation written by the same decision-maker cannot establish blindness or causal independence. The M13 sequence demonstrates why “fixtures predate the final draft edit” is insufficient. Known historical defects may validly be retested, but those outcomes must be labeled targeted rechecks rather than prospective oracle evidence.
4. **Oracle population can be post-hoc while snapshots remain intact.** Hashing the final population detects later mutation only relative to a committed manifest; it cannot prove that the first committed expectations were selected without access to draft outcomes. Nor does checking only listed files catch omitted cases unless the manifest itself is authoritative and the gate rejects unlisted inputs, duplicate identities, and changed path-to-hash mappings.
5. **Self-reported evidence is not durable order evidence.** Round-20 closure also found detailed harnesses, input manifests, and raw outcomes left only under `/tmp` (`round-20-verifier-spotcheck.md:78`), preventing durable replay/review. A report saying “before” or retaining only a final digest repeats the process weakness rather than repairing it.

## Required durable order receipts

A defensible sequence needs content-addressed, durable, append-only records; each record must include the prior receipt hash and be committed before the next event:

1. **Registration/seal receipt, before opening or measuring the candidate:** full commit OID and tree digest; complete claim/rubric and acceptance rules; baseline and candidate identity; exact oracle/resource/corpus manifest digests; case identity and semantic rationale; author/reviewer roles; and declared measurement protocol. The fixture bytes and their authoritative manifest must be sealed in that commit, not merely named in prose.
2. **Oracle-authorship receipt, also before candidate exposure:** per-case author and independent reviewer, fixture and expectation digests, semantic reason/source receipt, and explicit disposition of inherited known defects versus new prospective cases. Preserve the review/receipt as committed bytes. “No contact with the implementation author” is useful process policy, but is not itself proof of blinding; disclose the limit if no independently witnessed authoring record exists.
3. **Runner-captured before receipt for every measurement:** exact argv, cwd, relevant environment/tool/runtime identity, input-manifest hash, source snapshot hash (including uncommitted/untracked content), exit/status/output hashes, and registration/fixture commit IDs. The runner should refuse to label a run preregistered unless the sealed registration is an ancestor and the exact tested source/input identities match the receipt; store the receipt in a durable commit chained after registration, not `/tmp` or an editable report.
4. **Implementation and after receipts:** record the exact implementation commit/tree and repeat the same fixed inputs with output receipts chained after the sealed registration and before receipts. Preserve failed, skipped, corrupt, and could-not-evaluate outcomes; never replace the registered population or edit its expectations in place.
5. **Trust boundary:** commit ancestry plus hashes proves ordering/identity only inside the recorded repository history. For a claim about real-world ordering, receipts need an independently controlled monotonic witness (for example, a signed append-only receipt service or a trusted external timestamp), or the report must explicitly say that earlier unrecorded measurements cannot be ruled out. No artifact-only check can prove the absolute negative “nobody measured this elsewhere first” from self-authored timestamps alone.

## Smallest safe correction

Keep the current pre-measurement registration and the clarified rejection of a fake historical baseline; these are improvements. Tighten the C2 acceptance rule so it **requires** an append-only, runner-generated receipt chain binding the sealed registration, oracle fixture manifest, exact measured source snapshot, and every red/green run. Reject missing, late, inconsistent, or unbound receipts as **could-not-evaluate**, not clean. If prior sandbox exposure cannot be excluded by that chain/witness, classify that population as a targeted recheck and author a fresh sealed prospective set before candidate exposure. A Git timestamp or a registration-as-ancestor check alone is not an adequate M13 repair.
