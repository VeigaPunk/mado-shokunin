Apr 24, 2025
I have been facing some strangeness with my keyboard layout configuration.
Apparently randomly, I haven't observed any coincidences or correlations, my laptop's internal keyboard (at-translated-set-2-keyboard) switches back to the default English (US) layout. Or at least, it randomly starts outputting QWERTY.
This happens:
in the middle of typing a sentence
after switching between another window and VS Code
normal key presses still follow the Colemak-DH layout
shortcuts (Ctrl+C/V/Z, etc) use QWERTY
restarting VS Code fixes this problem
after launching Factorio
same behavior as VS Code, game respects Colemak-DH
except for shortcuts (Ctrl+C, etc)
does not happen if using XWayland
I can mitigate these problems by:
starting from English (Colemak-DH) while the "shortcut paradox" is happening
Close the game/code editor
switching back to English (US)
switching back to English (Colemak-DH)
Open the game/code editor
For VS Code, all windows need to be closed before switching to/from Colemak-DH.
This might be two separate issues:
the keyboard switches its layout and starts using QWERTY in the middle of typing
the custom layout continues to apply for normal key-presses, but shortcuts use QWERTY
In both circumstances, checking hyprctl devices always shows me the layout I expect to be in (Colemak-DH).
Keyboard at 28a1c470:
at-translated-set-2-keyboard
rules: r "", m "", l "us,us", v ",colemak_dh", o ",caps:ctrl_modifier"
active keymap: English (Colemak-DH)
capsLock: no
numLock: no
main: no
It is probably worthwhile to note that I am using Waybar with the "hyprland/language" widget to display the keymap at the top of the screen at all times. So far as I have noticed, it always agrees with hyprctl devices.
"hyprland/language" = {
keyboard-name = "at-translated-set-2-keyboard";
format = "󰌌 {}";
on-click = commands.keyboardLayoutNext;
on-click-right = commands.keyboardLayoutPrev;
};
The commands commands.keyboardLayoutNext and keyboardLayoutPrev call out to a custom script: https://github.com/spikespaz/dotfiles/blob/976c89f93fdfd6b75eb32f0f8403dc6d9a251d35/users/jacob/hyprland/scripts/switch-keyboard-layout.nu
My configuration for Hyprland looks like this:
wayland.windowManager.hyprland.config = {
input.resolve_binds_by_sym = true;
};
wayland.windowManager.hyprland.deviceConfig = {
"at-translated-set-2-keyboard" = {
kb_layout = "us,us";
kb_variant = ",colemak_dh";
kb_options = ",caps:ctrl_modifier";
};
};

I faced a similar issue, and it turned out to be because I was using Kanata. I checked hyprctl devices and saw this:
Keyboard at 404e3560:
at-translated-set-2-keyboard
rules: r "", m "", l "us, latam", v "", o "grp:alt_space_toggle"
active layout index: 1
active keymap: Spanish (Latin American)
capsLock: no
numLock: no
main: no
Keyboard at 404e2950:
kanata
rules: r "", m "", l "us, latam", v "", o "grp:alt_space_toggle"
active layout index: 0
active keymap: English (US)
capsLock: no
numLock: no
main: yes
I noticed that kanata was available as a separate "device" and that it showed the actual active layout.
So I changed this Waybar config:
"hyprland/language" = {
format = " ({shortDescription})";
"keyboard-name" = "at-translated-set-2-keyboard";
"on-click" = "hyprctl switchxkblayout at-translated-set-2-keyboard next";
};
To this one:
"hyprland/language" = {
format = " ({shortDescription})";
"keyboard-name" = "kanata";
"on-click" = "hyprctl switchxkblayout kanata next";
};
And now it works as expected. I hope it helps!
